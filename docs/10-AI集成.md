# 10 · AI 集成：专家与技能

这套方法最终要被 AI 消费。为此提供两类可复用资产：**八个专家**（定义角色、权限与纪律）和**二十二个技能**（定义动作与接口）。它们是纯文本，既能装进 WorkBuddy，也能作为任意 Agent 的 system prompt / tool spec 使用。

v1.2.0 起分两层：**方法论仓库是唯一权威源**（随 tag 发版、整包摘要写进账本），
**目标项目经升级 M7 得到只读部署副本** `.workbuddy/experts/` / `.workbuddy/skills/`，
由 `ASSET_MANIFEST.json` 与 `governance_meta.installed_assets` 双重绑定；路由真正读取副本正文。
副本逐字节一致、禁止项目内编辑，手改即判 drift。详见 [19-专家与技能可用](19-专家与技能可用.md)。

v1.0.0 起，权限不再只写在散文里：`agent_gateway.py` 是唯一写入口，
**只把它注册为 Agent 的写工具**，其余写入脚本保留为人工逃生舱。详见 [17-多Agent接入控制](17-多Agent接入控制.md)。

专家之间不靠"谁更懂"来竞争，而由确定性的 `expert-route` 按项目状态与任务意图选唯一负责人；交接协议见 [12-专家路由](12-专家路由.md)。

## 二、安装到 WorkBuddy

```bash
# 技能：复制全部二十个目录到用户级 skills
cp -r skills/expert-route skills/project-discover skills/project-bootstrap \
      skills/doc-rebuild skills/graph-compare \
      skills/ledger-scan skills/ledger-verify skills/ledger-decide \
      skills/ledger-lesson skills/ledger-guard skills/scenario-guard \
      skills/layout-inspect skills/ledger-upgrade skills/agent-gate \
      skills/method-assets skills/board-layout skills/scale-budget \
      skills/asset-install skills/test-map skills/work-panel \
      ~/.workbuddy/skills/

# 专家：把 EXPERT.md 作为专家包主体；或在会话中直接作为角色提示词加载
cp -r experts/ledger-steward experts/expert-router experts/greenfield-architect \
      experts/project-archaeologist experts/evidence-auditor experts/loop-executor \
      experts/release-steward experts/platform-steward \
      ~/.workbuddy/experts/
```

技能使用标准 `SKILL.md` frontmatter（`name` / `description` / `metadata`），与 WorkBuddy 现有技能格式一致。`description` 中的中英文触发词决定何时被调用。专家包同理，只是主体文件为 `EXPERT.md`。

以上是**人工全局安装**。若要让某个被治理项目自带可用资产（且可被门禁校验），用升级链路：

```bash
python3 scripts/upgrade.py --target P apply --approved-by "审批人姓名"   # M7 自动安装
python3 scripts/asset_bundle.py install --target P --apply --approved-by "审批人姓名" --json  # 单独补装
python3 scripts/asset_bundle.py verify --target P --json                  # 逐文件校验，手改即报 drift
python3 scripts/route_expert.py --check-assets --json                     # 路由消费的资产正文是否齐备
```

`--apply` 一律需要人批准；AI 不得自行改写项目里的专家/技能。安装位置是**项目级**
`.workbuddy/`，与用户级 `~/.workbuddy/` 不冲突。

## 三、平台无关的接入方式

不使用 WorkBuddy 的 Agent 也能接：

1. 把对应专家的 `EXPERT.md` 正文作为 system prompt（先由 `expert-router` 决定用哪一个）；
2. 把二十个 `SKILL.md` 的「输入 / 输出契约 + 步骤」作为工具描述；
3. 工具实现就是仓库里的脚本：`route_expert.py` / `discover_project.py` / `init_project.py` / `file_layout.py` / `build_capability_model.py` / `verify_ledger.py` / `ledger_decide.py` / `ledger_lesson.py` / `upgrade.py` / `agent_gateway.py` / `method_assets.py` / `asset_bundle.py` / `board_contract.py` / `scale_budget.py` / `scale_probe.py` / `work_panel.py` / `test_modules.py` / `check.sh`。

所有工具都是标准库 Python 或 shell，无 MCP、无网络、无密钥依赖。

## 四、最小消费路径

一个编码代理接手迭代，只需读三样东西：

```
DECISION_LEDGER.json
├── capability_model.next_queue   ← 一条任务：code / 等级跃迁 / 缺什么证据 / 关联文档 / 相关经验
├── lessons.items                 ← 已确认经验（任务卡已按 scope 附好，无需另查）
└── history.events                ← 该能力做过什么变更（可回放）
```

执行顺序：

```
expert-route（确定负责人）
→ 首次接入：project-discover → project-bootstrap（或空目录直接 bootstrap）
→ ledger-scan → ledger-verify → 取 next_queue 一条 → 补证据
→ ledger-scan → ledger-verify → ledger-lesson（若有新经验）
→ 重新 expert-route（状态可能已从 brownfield 变为 governed）
```

任何 `verify` 失败立即停止，先修账本。路由输出 `needs_clarification` 或 `blocked=true` 时，本轮不得进入编码。

## 五、权限边界（给 Agent 的硬约束）

- 可读：账本、历史、经验、源码、文档、`expert-route` 的只读扫描结果；
- 可写：按角色限定——路由不写；盘点只写草稿与报告；初始化写治理骨架；账本治理写 `entries` 与 `lessons.items`；执行专家写 `src/**` / `tests/**` / 测试记录；
- 禁止：手改 `level` / `completion` / `history.events` / 看板 `EMBED`；禁止把 `proposed` 直接改成 `done`；禁止替人决定业务优先级；禁止在冲突未澄清时继续写。

这些边界同时写进八份 `EXPERT.md` 与各技能，并由 `route_expert.py`（fail-closed）、`discover_project.py`（草稿保护）、`init_project.py`（跳过既有文件）、`ledger_decide.py` / `ledger_lesson.py`（写入纪律）在代码层强制——不依赖 Agent"记得遵守"。

**但 v0.9.0 的边界只在散文与建议里**：只要 Agent 有 shell，就能直接调用写入脚本绕过全部纪律。
v1.0.0 补上执行点 `agent_gateway.py`：默认拒绝的九道门（身份 / 角色 / scopes / CAS / registry 摘要 /
租约 / 人批准 / 生命周期 / 场景预检），许可与拒绝都写进账本内 append-only 的 `access.audit`。

接入顺序是硬约束：

```
upgrade.py plan → apply --approved-by <人> → post_upgrade（重新取证）
→ agent_gateway.py register --approved-by <人> → status 取指纹与 registry 摘要
→ request（默认 dry-run）→ request --apply → 重新 expert-route
```

平台注入时**只把 `agent_gateway.py status/request` 注册为写工具**，
`ledger_decide.py` / `ledger_lesson.py` / `lifecycle.py` 保留为人工逃生舱，不暴露给 Agent。
网关是策略执行点而非 OS 沙箱，完整边界见 [17-多Agent接入控制](17-多Agent接入控制.md)。

## 六、验证 Agent 是否真的按纪律工作

v1.2.0 起仓库自身测试按 6 个开发模块组织（`tests/MODULES.json` 是唯一清单，
文件内 `MODULE_ID` 自证，`run_tests.py` 的 `rglob` 与 `unittest discover` 双口径交叉验证）；
`scripts/test_modules.py --target P` 还能列出被治理项目中缺单测的能力模块，详见
[20-测试架构与模块映射](20-测试架构与模块映射.md)。

`tests/routing/test_skills.py` 用负向用例证明纪律生效。`tests/routing/test_routing.py` / `tests/adoption/test_discovery.py` / `tests/adoption/test_bootstrap.py` 证明多专家边界。`tests/traceability/test_trace_docs.py` / `test_trace_arch_git.py` / `test_compare_graphs.py` 证明可追溯闭环：文档可重建、目标可从文档抽取、git 路径可回连决策与事件、规划/实际差距会被正确分派给专家。`tests/meta/test_layout.py` 证明文件布局清单与产出脚本不漂移、`--diff` 全程只读、越界报告会被拦截。`tests/meta/test_upgrade.py` / `tests/meta/test_agent_gateway.py` 证明升级必须人批准且有备份/回滚、网关默认拒绝、越权与并发被拦、写入后 26 条不变量仍全绿。`tests/meta/test_platform_contract.py` 证明资产/骨架漂移会被发现、归一化不破坏账本数据、治理文件数不随项目规模增长；`tests/views/` 的四个新模块证明只读副本、节点工作台与新看板视图。跑法见 [循环协议](05-循环协议.md)、[专家路由](12-专家路由.md)、[可追溯性](13-可追溯性.md)、[场景矩阵](14-场景矩阵.md)、[文件架构](15-文件架构.md)、[升级与迁移](16-升级与迁移.md)、[多 Agent 接入控制](17-多Agent接入控制.md)、[规模化与版面契约](18-规模化与版面契约.md) 与 `bash scripts/check.sh`。另见 [19-专家与技能可用](19-专家与技能可用.md)、[20-测试架构与模块映射](20-测试架构与模块映射.md)、[21-节点工作台与看板视图](21-节点工作台与看板视图.md)。
