# 10 · AI 集成：专家与技能

这套方法最终要被 AI 消费。为此提供两类可复用资产：**六个专家**（定义角色、权限与纪律）和**八个技能**（定义动作与接口）。它们是纯文本，既能装进 WorkBuddy，也能作为任意 Agent 的 system prompt / tool spec 使用。

专家之间不靠"谁更懂"来竞争，而由确定性的 `expert-route` 按项目状态与任务意图选唯一负责人；交接协议见 [12-专家路由](12-专家路由.md)。

## 一、资产清单

| 资产 | 位置 | 职责 |
|---|---|---|
| 专家 `expert-router` | `experts/expert-router/EXPERT.md` | 只读判定状态与意图，选唯一负责人；冲突要求澄清 |
| 专家 `greenfield-architect` | `experts/greenfield-architect/EXPERT.md` | 空目录新建：最小骨架、来源可追溯 |
| 专家 `project-archaeologist` | `experts/project-archaeologist/EXPERT.md` | 存量项目：只读盘点、草稿优先、绝不覆盖 |

| 专家 `evidence-auditor` | `experts/evidence-auditor/EXPERT.md` | 只读门禁与 21 条不变量，失败即冻结 |

## 二、安装到 WorkBuddy

```bash
# 技能：复制全部八个目录到用户级 skills
cp -r skills/expert-route skills/project-discover skills/project-bootstrap \
      skills/ledger-scan skills/ledger-verify skills/ledger-decide \
      skills/ledger-lesson skills/ledger-guard \
      ~/.workbuddy/skills/

# 专家：把 EXPERT.md 作为专家包主体；或在会话中直接作为角色提示词加载
cp -r experts/ledger-steward experts/expert-router experts/greenfield-architect \
      experts/project-archaeologist experts/evidence-auditor experts/loop-executor \
      ~/.workbuddy/experts/
```

技能使用标准 `SKILL.md` frontmatter（`name` / `description` / `metadata`），与 WorkBuddy 现有技能格式一致。`description` 中的中英文触发词决定何时被调用。专家包同理，只是主体文件为 `EXPERT.md`。

## 三、平台无关的接入方式

不使用 WorkBuddy 的 Agent 也能接：

1. 把对应专家的 `EXPERT.md` 正文作为 system prompt（先由 `expert-router` 决定用哪一个）；
2. 把八个 `SKILL.md` 的「输入 / 输出契约 + 步骤」作为工具描述；
3. 工具实现就是仓库里的脚本：`route_expert.py` / `discover_project.py` / `init_project.py` / `build_capability_model.py` / `verify_ledger.py` / `ledger_decide.py` / `ledger_lesson.py` / `check.sh`。

所有工具都是标准库 Python 或 shell，无 MCP、无网络、无密钥依赖。

## 四、最小消费路径

一个编码代理接手迭代，只需读三样东西：

```
DECISION_LEDGER.json
├── capability_model.next_queue   ← 一条任务：code / 等级跃迁 / 缺什么证据 / 关联文档 / 相关经验
├── lessons.items                 ← 已确认经验（任务卡已按 scope 附好，无需另查）
└── history.events                ← 该能力做过什么变更（可回放）
```

执行顺序：

```
expert-route（确定负责人）
→ 首次接入：project-discover → project-bootstrap（或空目录直接 bootstrap）
→ ledger-scan → ledger-verify → 取 next_queue 一条 → 补证据
→ ledger-scan → ledger-verify → ledger-lesson（若有新经验）
→ 重新 expert-route（状态可能已从 brownfield 变为 governed）
```

任何 `verify` 失败立即停止，先修账本。路由输出 `needs_clarification` 或 `blocked=true` 时，本轮不得进入编码。

## 五、权限边界（给 Agent 的硬约束）

- 可读：账本、历史、经验、源码、文档、`expert-route` 的只读扫描结果；
- 可写：按角色限定——路由不写；盘点只写草稿与报告；初始化写治理骨架；账本治理写 `entries` 与 `lessons.items`；执行专家写 `src/**` / `tests/**` / 测试记录；
- 禁止：手改 `level` / `completion` / `history.events` / 看板 `EMBED`；禁止把 `proposed` 直接改成 `done`；禁止替人决定业务优先级；禁止在冲突未澄清时继续写。

这些边界同时写进六份 `EXPERT.md` 与各技能，并由 `route_expert.py`（fail-closed）、`discover_project.py`（草稿保护）、`init_project.py`（跳过既有文件）、`ledger_decide.py` / `ledger_lesson.py`（写入纪律）在代码层强制——不依赖 Agent"记得遵守"。

## 六、验证 Agent 是否真的按纪律工作

`tests/test_skills.py` 用负向用例证明纪律生效：重复立项被拒绝、`confirmed` 缺 `action` 被拒绝、驳回无理由被拒绝。`tests/test_routing.py` / `test_discovery.py` / `test_bootstrap.py` 证明多专家边界：冲突会要求澄清、账本损坏会冻结、盘点不覆盖草稿、接入后生成与校验通过。跑法见 [循环协议](05-循环协议.md)、[专家路由](12-专家路由.md) 与 `bash scripts/check.sh`。
