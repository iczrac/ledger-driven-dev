# 34 · 运行时风险入口（v2.15.0）

把目标项目的 STATE 事件投影成**可追溯的运行时风险信号**，作为账本 `next_queue` 排序的
只读输入。它回答一个此前账本答不了的问题：**下一个该做的，是补证据，还是处理已经量到的真实风险？**

## 为什么需要它

账本擅长治理成熟度：等级、证据、决策、经验都能复算。但它默认是「文件视角」——
只要契约/实现/单测/测试记录齐了，能力点就会往上升。真实运行时的恶化（污染率单调上升、
provider 断供、覆盖缺口）如果不写进账本，SELECT 仍会把「补证据」排在前面。
这不是账本算错，而是输入缺了一路。

v2.13 的目标循环与 v2.14 的推广探路进一步暴露这个问题：循环能跑、判据能表达，
但取到的头号任务与现场 P0 无关。因此补一路**运行时风险入口**，而不是把风险硬编码进账本。

## 边界（不可协商）

- 权威源不变：`DECISION_LEDGER.json` 仍是唯一事实源；事件的权威源是 `STATE/events/*.md`。
- 只读投影：解析事件、产出信号、重排队列副本；不写事件、不写账本、不改目标项目。
- 风险不是证据：`risk_score` 只影响排序和任务卡注解，不改 `level / completion / evidence_tier`。
- fail-closed：置信度缺失/非法、无能力码命中、映射歧义 → 不进排序。
- 无第二事实源：信号是可序列化的投影，生成器把它当作 `f(...)` 的显式输入。

## 两段切片

| 切片 | 能力 | 落点 |
|---|---|---|
| Slice 1 | 解析 `## E<n>` 事件块 → 信号 → 域级重排 | `scripts/runtime_signals.py` 的 `parse_state_events / domain_hint / risk_score / apply_risk_signals` |
| Slice 2 | 精确能力点映射 + 生成器接入 | `capability_hits / project_signals / apply_risk_signals_exact`；`build_capability_model.py --runtime-signals` |

Slice 1 验证「风险能否改变方向」；Slice 2 验证「改的是对的那个能力点，而不是整个域」。

## 映射优先级

1. 事件显式字段 `capability / capabilities / target`：必须是账本中真实存在的 code；
2. 原文中的完整能力码：必须命中 `model` 全集；
3. 语义词表：按更长关键词优先；同长跨 token 命中判歧义并丢弃；
4. 表外文本不硬塞，未知置信度直接丢弃。

语义词表是**投影规则**，可审计可改；它不是事实，也不替代事件作者显式标注能力码。

## 生成器契约

```bash
python3 -c 'import json; from runtime_signals import parse_state_events, project_signals; ...' > signals.json
python3 governance/build_capability_model.py --root . --runtime-signals signals.json --dry-run
python3 governance/build_capability_model.py --root . --runtime-signals signals.json --check
```

- 不给 `--runtime-signals`：队列形状与旧行为完全一致；
- 给出该参数：命中的任务卡新增 `risk_score / risk_signal / risk_evidence`，
  排序键为 `(-risk_score, completion, code)`；
- `--check` 同步比对风险注解，手改或漏信号都会报漂移；
- 实现与示例的三份生成器副本必须逐字节一致。

## 取证结论

在干净快照上的只读取证：17 个事件块 → 3 条精确投影；头号任务由「补证据」变为
带 `E4` 原文可追溯的运行时风险点；此前 Slice 1 的域级抬升导致的同域误伤
（例如把“只覆蓋 3 個檔案”当覆盖审计）在收紧词表后回落。详见
`feedback/RUNTIME-SIGNALS-SLICE1.md` 与 `RUNTIME-SIGNALS-SLICE2.md`（脱敏 `P.*`）。
