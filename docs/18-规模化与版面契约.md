# 18 · 资产升级、看板版面与大规模项目

> 三个反问：**专家和 skill 是否一起升级？项目 HTML 是否已设定统一样式、避免差异化版面？
> 项目大、需生成的文件数量大时有没有对应考量？**
> 本文给出结论、可执行的契约与实测数据；相关实现是 `method_assets.py`、
> `board_contract.py`、`scale_budget.py`、`scale_probe.py` 与 `templates/index.html.template`。

## 一、三问的结论

| 问题 | v1.0.0 的答案 | v1.1.0 补齐 |
|---|---|---|
| 专家 / skill 是否一起升级 | 随方法论仓库 `git tag` 一起发版，但目标账本**没有任何字段**记录这批资产；用旧专家卡指挥新骨架不会被发现 | 整包资产摘要写进 `governance_meta.method_assets`；资产变化即要求重新批准升级（M5） |
| HTML 是否统一样式 | 模板有完整 CSS/DOM/JS，但同步器只替换 `EMBED` 数据段，24 条不变量也只校验数据；项目手改 CSS 或留着旧模板不会变红 | 去 EMBED 后的**骨架 sha256** 契约 + M6 归一化 + 统一 `PAGE_SIZE` 分批渲染 |
| 项目大 / 文件多 | 治理层文件数本来就固定，但**没有**预算、阈值、分页或可复现基准 | 只读规模预算 + 真实生成器基准 + 7 个视图分批渲染；诚实保留 S2 残差 |

一句话：**这三者都不是新功能，而是「判定规则本身」与「呈现规则」的一致性约束**。
缺了它们，`verify` 可以全绿，但项目实际在用旧专家、旧版面、超预算的账本。

**v1.2.0 的深化**：v1.1.0 回答的是「一致」，v1.2.0 回答的是「可用」与「可利用」。
专家 / 技能从「只有摘要」升级成**项目内只读部署副本**（M7，`installed_assets` 逐文件绑定）；
看板从 8 个 tab 的浏览器升级成 10 个 tab 的**节点工作台**，在模块 / 组件 / 能力点上
直接显示 TODO、issue、逐用例测试结果与健康度；规模预算新增 `work_items` 一项。
分别见 [19](19-专家与技能可用.md)、[21](21-节点工作台与看板视图.md)、[20](20-测试架构与模块映射.md)。

## 二、升级范围：两类资产，一条链路

| 类别 | 内容 | 升级方式 | 是否进目标项目 |
|---|---|---|---|
| A 方法论仓库资产 | `experts/`、`skills/`、`scripts/route_expert.py`、`templates/`、`docs/01-21` | 提交 + 打 tag（`git pull` / checkout tag） | **部分**：权威源不复制；专家/技能经 M7 装成只读副本 |
| B 目标项目治理骨架 | 3 个 `governance/*.py` 副本 + 账本内 `governance_meta` / `access` + 看板骨架 | `upgrade.py` 人批准 `apply` | 是 |
| C 账本数据契约 | `ledger_version` 结构 | 仍只 fail-closed，不做自动迁移 | 是（数据） |

A 变了不会自动改 B，但会让 `method_assets` 摘要变化，于是 B 的 `plan` 必须列出 M5、
`verify` 不再允许 `upgrade_complete=true`。v1.2.0 起还要列出 M7：把 28 份专家/技能
装成项目内**只读部署副本**，由 `ASSET_MANIFEST.json` 与 `governance_meta.installed_assets`
逐文件绑定；`asset_bundle.py verify` 检查逐字节一致，手改即判 drift。

所以是**两层绑定、一份权威源**：整包摘要回答「用哪批规则」，逐文件摘要回答「副本有没有被改」。
副本与权威源逐字节相同、禁止项目内编辑，唯一修复是重新人批准安装，因此不产生第二事实源。

```text
改专家/技能/模板/文档 → method_assets.py 摘要变化 → 发 tag
   → upgrade.py --target P plan --json（assets / board / installed 段 + M5 / M6 / M7 / M8）
   → 人批准 apply（写摘要、装只读副本、统一骨架、初始化工作台、先备份）
   → asset_bundle.py verify + route_expert.py --check-assets（副本可用且路由读到）
   → verify 12 项 → post_upgrade 19 步 → 交回 expert-router
```

资产组与下限（`method_assets.py --check` 强制）：experts ≥ 8、skills ≥ 20、scripts ≥ 26、
templates ≥ 4、编号文档 ≥ 21、STANDARD = 1。派生生成物不纳入，避免每次生成都变摘要。
其中可安装资产（`asset_bundle.py --check`）为 8 份 `EXPERT.md` + 20 份 `SKILL.md` = 28 份。

## 三、看板版面：数据契约 ≠ 版面契约

`ledger_io.sync_board()` 与生成器只替换 `const EMBED = {...};\nlet DATA`。
**其余字节一律原样保留**——这是 v1.0.0 的真实行为，不是 bug，但意味着
「EMBED 一致」无法证明「CSS/DOM/JS 一致」。

骨架摘要定义：把 EMBED 数据段换成固定占位符后，对剩余全部字节取 sha256。
于是账本数据怎么变都不影响摘要，而改一个 CSS 变量、删一个 tab、改一处 JS 都会变。

| 检查 | 管什么 | 工具 |
|---|---|---|
| `board_embed_synced`（24 条不变量之一） | 数据段与账本逐字节等价 | `verify_ledger.py` |
| `board_skeleton`（账本内字段） | CSS / DOM / JS 与权威模板一致 | `board_contract.py` / `upgrade.py verify` |
| `layout.missing_ids` / `style_bytes` | 结构锚点与样式体积的只读取证 | `board_contract.py check --json` |

**纪律**：要换样式只能改 `templates/index.html.template` → 发版 → 各项目经 M6 归一。
禁止在项目里改 CSS「追平」或自定义品牌化版面；那会产生第二套呈现规则。
归一化默认 dry-run，必须人批准；`upgrade.py` 统一快照已包含 `index.html`，
独立修复时 `normalize` 会把原看板存进运行时备份目录。

模板里的 `const PAGE_SIZE=200` 是统一分批上限：全部条目 / 待裁决 / 工作台 / 工作项 /
时间线 / 模块地图 / 架构钻取 / 能力地图 / 演进历史 / 经验库**十个视图**都按它截断
并给「显示更多」。节点工作条是每批卡片内的轻量聚合，不额外生成卡片。
`scale_budget.py` 直接解析该常量，预算口径与渲染实现不会各自漂移。

```bash
python3 scripts/board_contract.py --target P check --json          # 只读，漂移退出码 1
python3 scripts/upgrade.py --target P apply --approved-by "审批人姓名"  # 推荐：M6 统一归一
python3 scripts/board_contract.py --target P normalize --apply --approved-by "审批人姓名"
```

注意 `rollback` 会把看板恢复到升级前骨架；回滚后必须重新 `plan → apply → verify`，
不能只看账本字段就说升级完成。

## 四、项目变大：固定的文件数，增长的六个维度

治理层**文件数固定**：`registry.json` / `DECISION_LEDGER.json` / `index.html` /
4 个工具副本 / 少量派生报告。模块与能力增长不会「每模块生成一个文件」，
业务层的文件数本来就由项目自己决定。真正增长的是：

1. **账本体积**：`capability_model` + `history.events`，而每个事件都带**全量状态快照**；
2. **看板体积**：EMBED 把同一份账本再内联一次（离线可看的代价）；
3. **结构数量**：`entries` / `history_events` / `capabilities` / `test_inputs`；
4. **浏览器 DOM**：已由统一模板 `PAGE_SIZE` 分批解决；
5. **CPU**：生成器按能力逐个扫 `docs/` 与 `tests/`，接近 `O(能力 × 项目文件)`；
6. **工作态数据**（v1.2.0）：`work_items` 条数与 `test_results.cases` 逐用例明细；
   两者都进账本并内联到 EMBED，由 `work_items` 预算项与 `PAGE_SIZE` 共同约束。

### 实测基准（`scale_probe.py`，临时目录、标准库、同一份生成器）

| 能力 / 业务文件 / 决策 / 历史事件 | 生成器耗时 | 账本 | 看板 | 治理文件 | 预算 |
|---|---:|---:|---:|---:|---|
| 50 / 100 / 50 / 3 | 0.135s | 184.5 KiB | 118.4 KiB | 4 | ok |
| 400 / 500 / 200 / 30 | 0.723s | 2194.0 KiB | 939.6 KiB | 4 | warn |
| 1000 / 1500 / 500 / 80 | 4.406s | 9611.2 KiB | 3939.1 KiB | 4 | warn |

同一能力数下把业务文件从 40 增到 160，`governance_files` 完全不变
（`test_platform_contract.BudgetTest.test_probe_shows_file_count_stays_fixed` 证明）。
体积的主要来源是「事件数 × 能力数」，**不能靠删历史解决**——append-only 是历史可信的前提。

### 预算表（`scale_budget.py` 的 `BUDGETS`，单一事实源）

| 指标 | warn | hard | 超了怎么办 |
|---|---:|---:|---|
| 账本 / 看板体积 | 5 MiB | 20 MiB | 归档后复制新项目，不拆账本 |
| 决策条目 | 2000 | 10000 | 按阶段归档；看板已分批 |
| 历史事件 | 500 | 2000 | 不可删；冻结/归档后开新账本 |
| 能力点 | 2000 | 10000 | 拆 registry 到独立项目（E7 仍是 gap） |
| 测试绑定文件 | 1000 | 5000 | 按子项目分组跑报告 |
| 治理层文件数 | 40 | 80 | 先查是否出现第二事实源 |
| 项目文件总数 | 20000 | 100000 | 分仓 / 分项目；生成器全量重算 |
| 单视图卡片数 | 200 | 2000 | 模板已按 `PAGE_SIZE` 分批 |
| 节点工作项（TODO / issue） | 500 | 2000 | 关闭已完成项；按模块归档，不删账本 |

`status = ok | warn | exceed`；`--check` 只对 `exceed` 返回 2，`--strict` 让 `warn` 也失败。
**阈值是告警，不是自动降级**：AI 不得替人决定归档、拆项目或跳过门禁。

### 超预算流程

```text
scale_budget.py --target P --json --check     # 只读预算与建议
board_contract.py --target P check --json     # 确认仍是统一模板（含分批渲染）
scale_probe.py --mods 50 --caps 20 --files 1500 --events 80 --json   # 临时目录复现耗时
→ 由人决定：拆项目 / 冻结归档后复制 / 降低门禁频率
→ 交接卡写明 status、超标项与基准耗时，交回 platform-steward
```

**诚实残差**：生成器没有增量索引（场景矩阵 S2 = `partial`）；monorepo 多项目
联合门禁仍是 E7 = `gap`。超过 1 万能力或 2 万文件且门禁耗时不可接受时，
才值得引入缓存 / 分片，而且必须保持同一份账本仍可复算。

## 六、反模式

- **手工把专家/技能复制进目标项目**：唯一合法的安装路径是 M7 / `asset_bundle.py install --apply --approved-by`；
  手工复制没有 `ASSET_MANIFEST.json` 与 `installed_assets` 绑定，等于悄悄产生第二份规则。
- **在项目里编辑只读副本"顺手修个 bug"**：手改即 `drift`，应改方法论仓库并发版，再重新人批准安装。
- **为了让 `verify` 变绿手改 `method_assets.digest` / `installed_assets.digest` /
  `test_results.source_sha256`**：等于伪造版本绑定或伪造全绿。
- **在项目 `index.html` 里改 CSS 或加 tab**：制造差异化版面，且下次升级必被归一覆盖。
- **项目一大就拆账本 / 删 `history.events`**：破坏 A3 单一事实源与 append-only 历史。
- **只跑预算不跑基准**：阈值是静态估算，耗时与体积以 `scale_probe.py` 实测为准。
