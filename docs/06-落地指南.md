# 06 · 落地指南

从零接入一份项目，按下面步骤走。以 `examples/demo-shop` 为参照。

## 第 0 步：判断是否适合

适合：多模块、迭代周期长、决策容易散落、需要人机协作或 AI 接手的项目。
不适合：一次性脚本、单人短期玩具项目（收益小于维护成本）。

先跑一次**只读路由**，不要凭口头描述决定模式：

```bash
python3 scripts/route_expert.py --target /path/to/your-project --intent "接手现有项目"
```

- `greenfield-architect`：空目录，直接走下面的第 1 步新建；
- `project-archaeologist`：目录已有历史代码/测试/文档，先按第 1 步的「存量接入」分支盘点；
- `needs_clarification` 非空：说明意图冲突，先回答路由提出的问题再继续。

## 第 0.5 步：写入前预检（0.8.0 起必做）

路由只回答「谁来做」，预检回答「现在能不能动」。任何写入账本的动作之前跑一次：

```bash
python3 scripts/scenario_guard.py --target /path/to/your-project --json
```

出现 `block` 就先按 `fix` 处理：账本损坏、跨版本、冻结/归档、证据过期、并发指纹漂移、
绝对路径泄露都会阻止写入。`--strict` 下存在 block 时返回 2，可直接放进 CI。

并发或多 Agent 场景，把账本指纹带在手上：

```bash
FP=$(python3 -c "import json;print(json.load(open('governance/DECISION_LEDGER.json'))['capability_model']['history']['current_fingerprint'])")
python3 scripts/scenario_guard.py --target . --expect-fingerprint "$FP" --strict
python3 governance/build_capability_model.py --root . --expect-fingerprint "$FP" --strict-evidence
```

详见 [14-场景矩阵](14-场景矩阵.md)。

## 第 1 步：初始化骨架

新建项目：

```bash
python3 scripts/init_project.py \
  --target /path/to/your-project \
  --code MYPROJ \
  --name "我的项目" \
  --intent "新建项目"
```

存量项目（先只读盘点，再人工确认草稿）：

```bash
python3 scripts/discover_project.py --target /path/to/your-project --dry-run
python3 scripts/discover_project.py --target /path/to/your-project
# 编辑 governance/registry.draft.json：删非能力文件、合并重复域、校准 hints
python3 scripts/init_project.py --target /path/to/your-project --mode adopt \
  --from-draft /path/to/your-project/governance/registry.draft.json --code MYPROJ
```

两种模式都会生成 `governance/` 下的 6 个骨架文件：`registry.json`、`DECISION_LEDGER.json`、`index.html` 与三个工具副本（`build_capability_model.py` / `verify_ledger.py` / `run_tests.py`）。账本中的 `provenance` 会记录这是模板新建还是草稿接入——来源不可篡改，既有治理文件不会被覆盖。引入前后目录树与各文件含义见 [15-文件架构](15-文件架构.md)。

## 第 2 步：整理目录约定

生成器靠目录约定识别证据。按你的技术栈在 registry 里配置：

```json
"project": {
  "contracts_dir": "src/contracts",
  "unit_test_dir": "tests/unit",
  "test_record_dir": "docs/test_records",
  "docs_dir": "docs",
  "governance_dir": "governance",
  "governance_gate": true
}
```

路径相对项目根。若你的项目没有独立契约目录，可把 `contracts_dir` 指向接口定义所在目录，或接受这些能力停在 L2。

引入后随时可只读核对目录现状：

```bash
python3 scripts/file_layout.py --diff --target /path/to/your-project --strict
```

它会报告项目处于 `bootstrap / skeleton / governed` 哪个阶段、缺哪些必需骨架，
以及 `governance/` 里有没有清单外的自制报告（第二事实源）。完整清单见
[目录全量表](generated/FILE_LAYOUT.md)。

## 第 3 步：编写能力注册表（唯一需手写的清单）

在 `registry.json` 的 `modules` 里列出模块与能力点：

```json
{
  "code": "CORE",
  "name": "核心领域",
  "src": ["src/domain/"],
  "caps": [
    {
      "name": "订单领域模型",
      "domain": "ORDER",
      "impl": ["src/domain/order.py", "src/contracts/order_schema.py"],
      "hints": ["order"]
    }
  ]
}
```

要点：

- `code` / `domain` 用大写短码，一经分配不复用；
- `src` 是组件树扫描入口，可多个；
- `impl` 是证据 glob，命中真实文件才算有实现；
- `hints` 用小写英文，与单测/测试记录文件名保持一致——它决定 L3/L4 能否被识别。

## 第 4 步：试跑并校准

```bash
python3 governance/build_capability_model.py --root . --dry-run
```

打印每个能力的等级与完成度。对照实际检查：

- 明明有单测却停在 L2？→ `hints` 没匹配上测试文件名；
- 明明有测试记录却停在 L3？→ 检查 `test_record_dir` 与文件名关键字；
- 不该有 L5 却给了 L5？→ 检查 `governance_gate`。

校准到符合预期再正式生成。

## 第 5 步：正式生成

```bash
python3 governance/build_capability_model.py --root .
```

产出：账本里的 `capability_model` + `architecture`，并同步看板内嵌数据。

## 第 6 步：迁入历史决策

把散落的重大决策整理进 `entries`。一条一条来，优先迁「还在影响当前决策」的。旧报告保留为历史证据，不再维护。

## 第 7 步：接入迭代习惯

- 代码/测试/文档变更后：重跑生成器；
- 有重大决策：写进账本，不新建报告；
- 每周看一次「待裁决」视图，清理 `proposed` / `deferred`；
- 想让 AI 接手：按 [05-循环协议](05-循环协议.md) 的六步走。

## 常用命令

```bash
# 只打印摘要，不写文件
python3 governance/build_capability_model.py --root . --dry-run

# 自定义配置文件路径
python3 governance/build_capability_model.py --root . \
  --registry path/to/registry.json \
  --ledger path/to/DECISION_LEDGER.json

# 只生成账本，不同步看板（比如看板正在被别人编辑）
python3 governance/build_capability_model.py --root . --no-board
```
