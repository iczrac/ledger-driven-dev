# 15 · 引入后的文件架构

## 为什么

前十四篇回答的是「怎么治理」，没回答一个接手者最先问的问题：**把这套方案装进项目之后，磁盘上到底多出什么？哪些目录能改、哪些不能碰？**

这个问题不写清楚会产生三类真实事故：

1. 有人把 `governance/` 当成又一个报告目录，往里新建 `STATUS.md` —— 出现第二事实源；
2. 有人手改 `docs/generated/CAPABILITY_INDEX.md` 修错别字 —— 下次重跑被覆盖，且文档与账本短暂不一致；
3. 有人以为 `lifecycle.log` 是文件，在 `governance/` 里找不到就自己补一个 —— 状态机从此分裂。

所以本篇不靠叙述，而是由 [`scripts/file_layout.py`](../scripts/file_layout.py) 定义一份**可执行目录清单**：`--check` 把清单与产出脚本源码交叉验证，`--diff` 只读检查任意项目的现状，[`generated/FILE_LAYOUT.md`](generated/FILE_LAYOUT.md) 是同一份定义渲染出的全量表。

## 一、核心结论

**引入方案 ≠ 重构项目。** 业务代码、测试、原有文档的位置一个都不动；项目根新增两个必需目录，升级 M7 后再按需多一个资产层：

| 新增 | 作用 | 谁负责 |
|---|---|---|
| `governance/` | 事实源、派生报告、工具副本 | 初始化器建骨架，生成器 / 校验器 / 决策脚本维护 |
| `docs/generated/` | 机器渲染的规范化项目文档 | `rebuild_docs.py` / `compare_graphs.py` |
| `.workbuddy/`（按需） | 专家 / 技能的**只读部署副本**，让平台能直接加载 | `asset_bundle.py`（升级 M7 或单独人批准安装） |

方法论仓库自身（`experts/`、`skills/`、`scripts/`、`templates/`、`tests/`、`docs/01-21`、`examples/`、CI 配置）**不复制进被治理项目**。例外有两类：四个工具脚本以 `governance/*.py` 副本落地，让项目脱离本仓库也能独立复算证据；专家与技能在 v1.2.0 起经人批准安装为**只读部署副本** `.workbuddy/experts/` / `.workbuddy/skills/`，权威源仍只在方法论仓库，副本逐字节一致且禁止项目内编辑。

因此版本绑定也是两层：整包摘要 `governance_meta.method_assets` 说明「用的是哪一批规则」，逐文件摘要 `governance/ASSET_MANIFEST.json` + `governance_meta.installed_assets` 说明「项目里这 28 份副本有没有被改过」。看板样式仍只由 `templates/index.html.template` 统一发放。详见 [18](18-规模化与版面契约.md) 与 [19](19-专家与技能可用.md)。

按所有权分七层（v1.0.0 新增运行时层，v1.2.0 新增资产层）：

```
工具层     governance/*.py            模板副本，只读运行
草稿层     governance/*.draft.json    存量接入临时候选（仅 adopt 路径）
事实源层   governance/registry.json + DECISION_LEDGER.json   唯一输入
派生层     governance/*.json 报告 + index.html + docs/generated/*   自动重算
运行时层   .ledger-upgrade/ + .ledger-write.lock   升级备份与写入互斥锁，不是事实源
资产层     .workbuddy/experts/ + .workbuddy/skills/   只读部署副本，禁止手改
业务层     src/ tests/ docs/          原有资产，位置不变
```

运行时层刻意放在**项目根而不是 `governance/`**：它不含项目状态，只是时间戳快照与瞬态锁；
放进治理目录会被 `--diff` 误判为第二事实源。资产层同样在项目根，因为它是平台约定的
Agent 资产目录；`--diff` 用 `presence="on-demand"` 标记它「没出现也正常」，
出现后则由 `asset_bundle.py verify` 做逐字节校验。详见 [16-升级与迁移](16-升级与迁移.md)
与 [19-专家与技能可用](19-专家与技能可用.md)。

方向永远是 `业务层 + 事实源层 → 派生层`，反过来手改派生层就是腐化。

## 二、引入前 / 引入后（新建项目）

引入前，一个最小项目通常长这样：

```
my-project/
├── src/                 业务代码
├── tests/               单元测试
└── docs/
    ├── plans/           规划文档
    └── test_records/    测试记录
```

`init_project.py --mode greenfield` 之后：

```
my-project/
├── src/                                    [不变] 业务代码
├── tests/                                  [不变] 单元测试
├── docs/
│   ├── plans/                              [不变] <HINT>_PLAN.md
│   ├── test_records/                       [不变] <HINT>_TEST_RECORD.md
│   └── generated/                          [新增] 机器渲染，禁止手改
│       ├── PROJECT_BRIEF.md                    目标 / 范围 / 现状
│       ├── MODULE_MAP.md                      模块 → 目录 → 编码
│       ├── CAPABILITY_INDEX.md                编码 → 文档 / 测试 / 代码 / 决策
│       └── GRAPH_DIFF.md                      规划图 vs 实际图 + 开发顺序
└── governance/                            [新增] 治理层
    ├── registry.json                          ★ 唯一手写清单
    ├── DECISION_LEDGER.json                   ★ 单一事实源（含派生字段）
    ├── index.html                             看板（EMBED 与账本等价）
    ├── build_capability_model.py              工具副本：重算
    ├── binding_advisory.py                    工具副本：证据绑定 advisory
    ├── derived_issues.py                      工具副本：派生 issue（v2.3.0）
    ├── verify_ledger.py                       工具副本：26 条不变量
    ├── run_tests.py                           工具副本：产出测试报告
    ├── test_report.json                       [按需] 机器可读证据
    ├── TARGET_ARCHITECTURE.json               [按需] 文档 → 目标架构
    ├── GIT_TRACE.json                         [按需] 提交 → 决策 / 事件
    ├── GRAPH_DIFF.json                        [按需] 图差异 + 执行顺序
    └── CODE_INDEX.json                        [按需] 编码 ↔ artifact 索引
```

★ 表示人或按纪律裁决才能写的输入；其余全部由脚本产出。带 `[按需]` 的文件不出现是**正常状态**，只在跑过对应命令后生成，不是缺失。

## 三、存量接入的差异

历史项目走 `adopt` 路径时，`governance/` 会先多出两个**草稿层**文件：

```
governance/
├── registry.draft.json     只读盘点候选（schema registry-draft/1）
├── ADOPTION_REPORT.md      候选模块 / 置信度 / 风险 / 下一步
└── ...（人工确认草稿后，才由 init_project.py 生成上面那套骨架）
```

三条硬约束：盘点**只读**、草稿**默认不覆盖**、草稿在人工精简前**不是事实源**。这正是 `project-archaeologist` 与 `project-bootstrap` 的交接点，详见 [12-专家路由](12-专家路由.md)。接入完成后草稿可以留档，但生成器永不读它。

## 四、目录含义与所有权

完整 27 条路径 + 10 个账本内字段（路径 / 层 / 来源 / 出现时机 / 谁写 / 写入方式 / 能否手改 / git 策略 / 保护机制 / 含义）见 [`generated/FILE_LAYOUT.md`](generated/FILE_LAYOUT.md)。这里只列最容易被误读的几条：

| 路径 | 关键含义 |
|---|---|
| `governance/` | 治理层唯一落点。清单外自制报告、第二份账本会被 `--diff` 报为越界文件 |
| `registry.json` | 全项目**唯一**需要手填的清单：模块、impls、hints、unit_test；不写等级、不写完成度 |
| `DECISION_LEDGER.json` | 既能写又不能乱写：`entries` 经 `ledger_decide.py` 写，`capability_model` / `history` / `lessons` / `lifecycle` 是派生字段 |
| `index.html` | 看板内嵌 `EMBED` 必须与账本逐字节等价；**去 EMBED 后的 CSS/DOM/JS 骨架**还需与权威模板一致（`board_contract.py`），统一按 `PAGE_SIZE` 分批渲染；禁止在项目里改样式 |
| `test_report.json` | `verified` 的唯一证据源；绑定测试源码 sha256，源码一改就判 stale |
| `docs/generated/` | 与人工 `docs/` 物理隔离；要长期手写补充请换文件名，别改生成物 |
| `governance/*.py` | 模板副本，不在目标项目里改；升级靠 `upgrade.py` 同步 `templates/` 与 `scripts/` |
| `.ledger-upgrade/backups/<id>/` | 升级前的账本/看板/registry/工具副本快照 + `manifest.json`；`rollback --approved-by <人>` 按清单恢复 |
| `.ledger-write.lock` | 多 Agent 网关的 `fcntl` 互斥锁；瞬态文件，不进 git、不参与结论复算 |

**账本内字段不是文件**：`capability_model`、`history.events`、`lessons.items`、`lifecycle` / `lifecycle.log`、`retired_caps`、`execution.claims`、`provenance`、`governance_meta` / `upgrade_log` / `method_assets` / `board_skeleton`、`access` / `access.audit` 都是 `DECISION_LEDGER.json` 里的 JSON 字段。`governance/` 下**不存在** `lifecycle.log`、`UPGRADE_LOG.md`、`AGENTS.yaml` 或独立审计文件；状态变更写进账本内的 append-only 数组，不碰 `history.events`，也不新建第二事实源。

## 五、谁在什么时候改哪些文件

| 动作 | 文件变化 | 执行者 | 保护 |
|---|---|---|---|
| 路由 / 预检 | 无（全只读） | `expert-router` / `scenario-guard` | 退出码不写盘 |
| 初始化 | 新建 `governance/` 6 文件 | `init_project.py` | 默认跳过既有文件；外部绝对路径脱敏 |
| 存量盘点 | 新建草稿 2 文件 | `discover_project.py` | 只读扫描、默认不覆盖、截断告警 |
| 手写清单 | 改 `registry.json` | 人 | `registry_impls_exist` 校验路径真实性 |
| 决策 / 经验 | 改账本 `entries` / `lessons.items` | `ledger_decide.py` / `ledger_lesson.py` | 拒绝重复立项、缺行动经验 |
| 重算 | 重写账本派生字段 + `index.html` | `build_capability_model.py` | 版本契约、CAS 指纹、冻结拒绝、stale 证据回落 |
| 跑测试 | 重写 `test_report.json` | `run_tests.py` | 源码绑定摘要 |
| 重建文档 | 写 `docs/generated/` 三件套 | `rebuild_docs.py` | `write-if-absent`，需 `--force` 才覆盖 |
| 取证 / 比对 / 索引 | 写 4 份 `governance/*.json` + `GRAPH_DIFF.md` | 四个 trace 脚本 | 默认不覆盖，置信度不足给 warnings |
| 冻结 / 归档 / 退役 / 领用 | 只改账本内状态字段，同步 `EMBED` | `lifecycle.py` | 人工批准门；归档为不可写终态 |
| 治理骨架升级 | 备份到 `.ledger-upgrade/`；同步 6 个工具副本；安装只读专家/技能副本；必要时用模板归一 `index.html` 骨架；写账本内 `governance_meta` / `access` / `method_assets` / `board_skeleton` / `installed_assets` / `work_items` / `test_results` | `upgrade.py` | 只读 plan（七轴比对）、人批准 apply、12 项 verify、可 rollback |
| 节点工作项 | 只改账本内 `work_items` / `test_results`，同步 `EMBED` | `work_panel.py` | 默认 dry-run，写盘需 `--apply --approved-by`；投影绑定报告字节 |
| 资产安装 | 写 `.workbuddy/` 只读副本 + `ASSET_MANIFEST.json` + 账本 `installed_assets` | `asset_bundle.py` | 幂等、人批准、手改即判 drift、回滚只移除升级前不存在的产物 |
| 多 Agent 写入 | 只改账本内 `access`（名册/租约/审计）与授权的状态字段，同步 `EMBED` | `agent_gateway.py` | 默认拒绝九道门 + CAS + 租约 + 审计 |

注意「重算」是**唯一**会覆盖既有派生文件的动作，其余脚本默认跳过既有产物。这就是为什么要区分 `rewrite` 与 `write-if-absent`：前者代表"这份文件必须等于事实源"，后者代表"这份文件是一次取证快照"。

## 六、生命周期中的目录变化

```
bootstrap     governance/ 6 文件；docs/generated/ 尚不存在
   ↓ 首次生成 → 账本 capability_model / history genesis，看板 EMBED 同步
governed      按需出现 test_report / 4 份 trace JSON / docs/generated/ 四件套
   ↓ 迭代 → 生成器重写派生层；历史 append-only；经验候选进任务卡
upgraded      .ledger-upgrade/backups/<id>/ 出现；账本内多出 governance_meta / access，目录数不变
   ↓ 注册 Agent → .ledger-write.lock 在首次写入时出现；审计进账本内 access.audit
frozen        目录不变，但 scenario_guard 阻止全部写动作，只读取证仍可用
   ↓ unfreeze --approved-by <人> 或 archive --approved-by <人>
archived      终态：生成器与 lifecycle 自身都拒绝写入；继续开发请复制新项目
```

冻结/归档**不会**产生新目录或备份文件，状态只写进账本内字段——所以 `git status` 干净不代表项目没被冻结，判断依据是 `scenario_guard.py` 与账本 `lifecycle.state`，不是文件系统。详见 [14-场景矩阵](14-场景矩阵.md)。

## 七、编码如何把文件串起来

四段式编码 `PROJ.MODULE.DOMAIN.NN` 是跨文件的身份证（详见 [03-编码与成熟度](03-编码与成熟度.md)）：

```
DEMO.CORE.PRICE.02
  → docs/plans/PRICING_ROADMAP.md（L1，文件名 HINT 与 registry hints 匹配）
  → tests/unit/test_pricing.py（L3，由 registry.unit_test 声明）
  → src/domain/pricing.py（L2，由 registry.impls 声明）
  → docs/test_records/PRICE_TEST_RECORD.md（L4）
  → 账本 capability_model.projects[].modules[].caps[]（等级 / 证据 / next_action）
  → 账本 entries D-NNN（决策）、history.events[]（状态变化）
  → GIT_TRACE.json.commits[]（哪些提交动过这些路径）
  → CODE_INDEX.json（把上述全部按编码聚合）
```

**HINT 必须与 `registry.json` 的 `hints` 一致**，否则生成器识别不到，能力不会升级——这是最常被忽略的命名约定，已沉淀为示例经验 `L-001`。命名与状态词规范见 [STANDARD](STANDARD.md)。

## 八、git 策略

建议提交：`governance/` 全部（含工具副本与按需报告）、`docs/generated/`、业务代码与测试。理由：派生层可复算，但提交后能离线审计、能在 CI 里比对漂移。

可选提交：`test_report.json` 与 4 份 trace JSON。它们是一次取证快照，CI 重跑会得到同等内容（报告含源码摘要，路径归一，无机器绝对路径）。

建议忽略：

```gitignore
__pycache__/
*.py[cod]
.DS_Store
*.tmp
```

不要为了"保持仓库干净"而忽略 `DECISION_LEDGER.json`——它是唯一事实源，不进版本控制就等于没有历史。也**不要**把 `governance/` 整个忽略：那会让 26 条不变量与看板同步检查失去可比对对象。

## 九、自查与接入

```bash
# 清单自检：与产出脚本源码交叉验证，防止「文档说的路径」和「代码写出的路径」漂移
python3 scripts/file_layout.py --check

# 只读看某个项目现在处在哪个阶段、缺什么、有没有越界文件
python3 scripts/file_layout.py --diff --target /path/to/project
python3 scripts/file_layout.py --diff --target /path/to/project --strict --json

# 重新渲染目录全量表（生成物，勿手改）
python3 scripts/file_layout.py --emit-md docs/generated/FILE_LAYOUT.md
```

`--diff` 输出 `bootstrap`（缺必需骨架）/ `skeleton`（有骨架未生成能力模型）/ `governed` 三态，以及 `added_present`、`missing_required`、`unexpected`。`--strict` 下发现必需缺失或 `governance/` 越界文件返回 2，可直接放进 CI。技能 `layout-inspect` 封装了这条路径，供 Agent 在接手项目时先跑。

## 十、边界与反模式

- **不改业务目录**：方法不要求把 `src/` 改成 `modules/`，也不要求迁移既有文档；只约定规划/测试记录的文件名 HINT。
- **不在 `governance/` 写第二份报告**：决策进账本 `entries`，人读的结论进 `docs/generated/`，不要新建 `governance/STATUS.md`。
- **不手改派生层**：看板 EMBED、等级、完成度、历史、经验候选、`docs/generated/*` 一律改事实源后重跑。
- **不把方法论仓库搬进项目**：`experts/`、`skills/`、`scripts/`、`tests/` 属于工具仓库；项目里只需要 6 个工具副本。唯一允许出现的是经 M7 安装的**只读**专家/技能副本，且必须由 `asset_bundle.py verify` 逐字节校验、禁止在项目里编辑。
- **不把账本内字段当文件找**：`lifecycle.log` / `capability_model` / `governance_meta` / `access` 在 JSON 里，不在目录里。
- **不把备份或锁当状态**：`.ledger-upgrade/` 是时间戳快照，`.ledger-write.lock` 是瞬态互斥；结论一律复算账本，不读它们。
- **清单不是许可证**：`--diff` 只检查「文件在不在、有没有越界」，不检查内容真实性；内容可信靠 26 条不变量（[08-可信性校验](08-可信性校验.md)）与场景预检（[14-场景矩阵](14-场景矩阵.md)）共同保证。
- **不覆盖人工内容**：除生成器的 `rewrite` 外，所有脚本默认 `write-if-absent`；`--force` 是显式决定，不是默认行为。
