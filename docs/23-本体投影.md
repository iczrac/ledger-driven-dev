# 23 · 本体投影（派生只读的元契约层）

> v1.5.0。**本体不是第二事实源**：它只是把散落在代码枚举、文档词表与不变量里的
> 隐式答案收成一份可机器复算的约束视图。删光派生文件也能从权威源逐字节复原。

## 一、为什么是「收」不是「建」

这套系统早就在回答本体的四问：什么东西存在（四段式编码与能力树）、能取什么值
（各脚本枚举）、彼此怎么连（嵌套与取代链）、什么必然为真（24 条不变量）。
问题不是没有本体，而是答案散落在至少 9 处：

- `docs/STANDARD.md` 第四章声称「状态词全项目统一」并只列 4 类，实际运行的是
  **9 套以上状态机**（决策 / 成熟度 / 经验 / 历史 / 工作项 / 用例 / 场景 / 校验 / 观察）；
- 账本 `fields` 只自述 `entries` 的 5 个字段，覆盖不到 `capability_model` /
  `work_items` / `test_results`；
- 关系基数在两处定义不一致：`registry.json` 顶层 `project` 是单数 dict，
  而派生能力模型含 `projects[]`（多项目仓库有 4 个项目）。此前只能靠
  「不跑生成器重算」人为回避，因为**没有机器能命名这是一条基数公理违例**。

所以 v1.5.0 做的最小动作是：把已有答案**显式化、分型、可复算**。

顺带纠正一处抽象错误：「状态词全项目统一」这句话本身写错了。9 套状态机属于
9 类不同实体，压成一个词表会丢语义。本体统一的是**形式**——`<Type>.field`——
而不是取值。

## 二、五条宪法约束

| 约束 | 内容 | 可验证方式 |
|---|---|---|
| C1 单一事实源 | 只有账本 / registry / 报告 / 观察包可写；本体与图永不手维护 | `build` 只读权威源 |
| C2 生成性 | `ONTOLOGY = f(权威源)`，两次 build 同一 digest | `digest` 连跑三次一致 |
| C3 无孤儿来源 | 每个来源带 `sha256`，`check` 重算比对；每条关系带 `derivation` 与 `source_ref` | `check` 的来源绑定校验 |
| C4 三值逻辑 | `pass / na / fail` 即 Kleene K3 的 `True / Unknown / False`；采用封闭世界 + 显式 Unknown | 未绑定记 `na` 而非通过 |
| C5 人批准写盘 | 写派生文件与观察包都需 `--apply --approved-by <人>` | 无批准人返回退出码 2 |

不引入 OWL / RDF / 图数据库与开放世界语义（OWA 会把「缺失」当成「不否定」，
正好复活 v0.5.0 修过的假绿灯）。分层是 TBox `ONTOLOGY.json`、ABox 实例、
RBox 确定性规则，全部 JSON + 纯 Python 零第三方依赖。

## 三、产物与命令

| 产物 | 性质 | 生成者 |
|---|---|---|
| `docs/generated/ONTOLOGY.json` | 派生只读，含 `source_refs` / 取值域 / 公理 / `ontology_digest` | `ontology.py build` |
| `docs/generated/ONTOLOGY.md` | 派生只读的人类视图 | `ontology.py emit-md` |
| `governance_meta.ontology_digest` | **账本第七轴**，只存可复算的 digest | `upgrade.py apply`（M5 分支） |
| `affected_axis=ontology` 观察 | 真实项目漂移，走四产物 triage | `ontology.py diff --target P` |

```bash
python3 scripts/ontology.py build --json                       # 只读取证
python3 scripts/ontology.py build --apply --approved-by <人>   # 写两份派生文件
python3 scripts/ontology.py check --json                       # 投影同步 + 来源绑定 + 词表一致
python3 scripts/ontology.py check --target P --json            # 目标项目三类漂移 + 第七轴
python3 scripts/ontology.py diff --target P --json             # 输出观察（dry-run）
python3 scripts/ontology.py diff --target P \
  --out feedback/observations.jsonl --apply --approved-by <人> # 回流
python3 scripts/upgrade.py --target P verify --json            # 复验含 ontology_binding
```

`check --target` 绝不写目标项目；`diff --target` 复用 `ledger_feedback.make_obs`，
不另造 `obs_id` 算法或字段契约。

## 四、三类漂移

| 漂移 | 触发条件 | 观察示例 |
|---|---|---|
| `polyseme_violation` | 账本顶层出现裸 `status` / `level` / `severity`，或词表 id 未限定为 `<Type>.field` | 同形异义词缺限定形式 |
| `cardinality_contradiction` | `registry.project` 是单数 dict，而 `capability_model.projects` 含 >1 个项目 | 命中公理 A4（Project 基数 1..N） |
| `undeclared_entity` / `undeclared_value` | 账本顶层键未登记，或 `entries[].status` 等取值不在声明域 | 非法状态词被拦，修复后 `check` 重新通过 |

声明值与代码枚举双向比对：只改代码不改 `STANDARD.md` 判 `undeclared_value`；
只改文档不改代码判 `undeclared_entity`。这条规则让「文档声称」与「实际运行」
无法各自漂移。

v1.5.0 首次运行就在真实存量多项目仓库上把此前模糊的 monorepo gap 命名为
`cardinality_contradiction`（4 个项目），并 triage 成
`tests/meta/test_ontology.py` 的负向回归——**观察包从 12 条 / 3 收敛
变为 13 条 / 4 收敛**。

## 五、第七轴为什么只存 digest

`upgrade.py apply` 在 M5 分支写入 `governance_meta.ontology_digest`，
不新增迁移（8 条迁移与 19 步升级后流程保持不变）。`upgrade.py verify`
新增 `ontology_binding` 一项：

- 字段缺失 → `na`（能力未启用，不算通过，也不阻止「升级动作完成」）；
- 与权威源一致 → `pass`；
- 不一致 → `warn`，要求重新 plan → 人批准 apply → 复验。

账本里存的是**可复算的摘要**，不是本体内容。本体本身只在派生文件里，
因此不构成第二事实源，也不会产生「改账本 → 改本体 → 又改账本」的自指。

## 六、明确不做

1. 不新增账本内 `ontology` 内容字段、不新增手写本体清单；
2. 不做词表归一——9 套状态机按实体分型；
3. 不把 `na` 当缺陷——它是显式 Unknown，只对关键路径启用 `--require-active`；
4. 不把大账本分片另建事实源——只能是同源只读投影；
5. 不在本版改 `registry` 数据形状。`registry/2` 留到 **v2.0.0**，且必须先由
   A4 公理定义「什么合法」再改「数据长什么样」，并需人批准数据迁移。
