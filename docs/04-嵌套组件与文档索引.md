# 04 · 嵌套组件与文档索引

这一章讲「怎么看得见」——模块内不止一层组件，能力/规划要能顺着索引点到对应文档。

## 一、嵌套组件树

真实项目里模块下面有子目录、子目录下面还有文件。扁平罗列会丢失结构，所以生成器从文件系统真实提取一棵嵌套树：

```
模块 M-CORE  （src: src/domain/）
└── domain/                    ← 目录节点
    ├── order.py               ← 文件节点（关键名优先）
    ├── pricing.py
    └── models/                ← 子目录（递归到 max_depth）
        └── ...
```

### 生成规则

- **入口**：registry 中 `modules[].src` 列出的目录；
- **递归**：目录 → 子目录 → 文件，最大深度 `max_depth=3`；
- **规模控制**：每层最多 `max_entries=12` 项，避免大仓库撑爆看板；
- **关键优先**：文件名命中 `engine|core|runner|service|...` 的关键模块排在前面，确保重要的先被看到；
- **过滤**：忽略 `.` 开头、`__pycache__`、`node_modules`、`.git`、`venv` 等噪声目录。

### 双重呈现

同一棵树写进两处：

- `capability_model.projects[].modules[].component_tree` —— 能力地图里模块下展示；
- `architecture.projects[].modules[].component_tree` —— 架构钻取里展示，并挂 `capability_codes` 反向引用。

于是「组件 ↔ 能力」双向可查：从组件能看到它支撑哪些能力，从能力能看到它的实现落在哪些文件。

## 二、文档索引（doc_index）

每个能力点生成一份 `doc_index`，分八类：

| 类别 | 来源 | 含义 |
|---|---|---|
| `plans` | docs/ 中规划/方案类 + 模块级规划文档 | 这个能力的规划依据 |
| `related_docs` | docs/ 中其他相关文档 | 背景说明 |
| `module_docs` | module_map 里登记的模块文档 | 模块级文档 |
| `contracts` | L1 证据 | 契约 |
| `impl` | L2 证据 | 实现 |
| `unit_tests` | L3 证据 | 单测 |
| `test_records` | L4 证据 | 测试记录 |
| `decisions` | 账本 entries | 关联决策（含状态） |

另有 `control_center` 记录对应页面与 section。

### 匹配逻辑

1. **按能力域 + hints 匹配文档名**：在 `docs_dir` 下递归找文件名含域代码或 hints 关键字的文档；
2. **分类**：文件名含 `plan|roadmap|方案|规划|guide|workflow|spec|设计|治理` 的归入 `plans`，其余归入 `related_docs`；
3. **模块文档继承**：模块级规划文档自动归入其下所有能力点的 `plans`（规划天然覆盖整个模块）；
4. **决策关联**：账本中 `scope` 匹配项目、且正文/证据含能力域或名称关键字的条目，关联进来；模块级 `decisions` 自动继承。

### 可见、可点

- 所有路径统一为**仓库根相对**（`examples/demo-shop/docs/...`），看板点击时拼 `../../` 打开；
- 生成器校验路径存在性——索引只指向真实文件，不造假链接；
- 能力地图里每个能力点**常显** 4 个关键文档链接，展开可看完整索引与关联决策。

## 三、为什么这样设计

> **索引的价值在于「点得开」，不在于「列得全」。**

一个能点开的文档链接，胜过十份写着「详见文档」却找不到路径的报告。所以本方法宁可让索引短一点、准一点，也不堆砌失效链接。

组件树同理：它回答的是「这个模块到底由什么组成」——用真实目录生成，就不会出现「架构图画的和实际代码对不上」的经典问题。
