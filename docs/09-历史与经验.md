# 09 · 历史层与经验层

快照只回答「现在是什么」。一套能持续迭代的账本还必须回答两个问题：

- **怎么走到今天** —— 谁在什么时候改了什么？改动是否可回放？被覆盖前的状态还在吗？
- **走过的路教会了什么** —— 为什么这个能力一直停在 L2？上次踩过的坑这次能不能自动提醒？

历史层回答第一个，经验层回答第二个。两者共享一条设计原则：**机器负责发现与记录事实，人负责赋予事实意义**。

---

## 一、历史层：append-only 的状态演进

### 1.1 为什么不能靠人记录

让人在每次迭代后写一条「日志」，结果必然是：忙的时候忘写、出事的时候补写、久了没人看。更致命的是，手写日志与账本状态可能不一致——日志说升级了，账本里还是旧等级。

所以历史必须由生成器从**真实派生状态**自动产生，而不是由人填写。

### 1.2 状态指纹：让"变化"可被机器判定

`build_capability_model.py` 对派生状态计算稳定指纹：

```
snapshot = { 能力编码: {等级, 完成度, 证据路径, 文档索引路径, 决策引用} }
fingerprint = sha256(规范化排序后的 snapshot) 的前 16 位
```

关键性质：

- **只覆盖派生状态**，不含生成时间、注释、字段顺序——所以重跑不会"制造"变化；
- **覆盖证据与文档路径**——文件增删、测试记录补齐都会前进，不只是等级变化；
- **16 位十六进制**，短到能在看板上显示，碰撞概率可忽略。

生成器把当前指纹与最后一个事件比对：

| 情况 | 行为 |
|---|---|
| 没有历史事件 | 追加 `#1 genesis`，把全部能力作为基线快照 |
| 指纹不同 | 追加 `#N change`，记录 diff + 当时的完整状态快照 |
| 指纹相同 | **什么都不做**（幂等）——重跑一百次也不会产生噪音 |

### 1.3 事件结构

```json
{
  "seq": 2,
  "ts": "2026-11-17 21:40 HKT",
  "type": "change",
  "fingerprint_before": "dd4b6ffc6cade331",
  "fingerprint_after":  "e3c959ccb2996cde",
  "changes": {
    "level_transitions": [{"code":"DEMO.CORE.PRICE.02","from":"L2","to":"L5"}],
    "completion_delta":  [{"code":"DEMO.CORE.PRICE.02","from":0.4,"to":1.0}],
    "evidence_changes":  [{"code":"DEMO.CORE.PRICE.02","added":[...],"removed":[]}],
    "added": [], "removed": []
  },
  "state_digest": { "DEMO.CORE.PRICE.02": {"l":5,"c":1.0,"e":[...],"d":[...],"dec":[]} },
  "trigger": "derive",
  "note": "证据 / 等级 / 文档索引变化，由生成器自动侦测。"
}
```

`state_digest` 是**当时完整能力状态的快照**，所以任意历史事件都能单独回放，不依赖"从头重放所有 diff"。

### 1.4 append-only 如何被验证

`verify_ledger.py` 用三条不变量把"不可篡改"变成可检查：

1. `seq` 从 1 连续递增，首事件 `fingerprint_before` 为 null；
2. 每个事件的 `fingerprint_before == 上一事件的 fingerprint_after`（链断裂即失败）；
3. 每个事件的 `state_digest` 重算指纹 == 记录的 `fingerprint_after`（事件内容被改即失败），且末事件指纹 == 当前账本指纹（账本被手改即失败）。

这三条合起来意味着：**删不掉中间事件、改不了事件内容、也改不了当前状态而不被发现**。

## 二、经验层：从信号到可复用结论

### 2.1 机器只识别信号，不下结论

生成器从历史里识别三类**可沉淀信号**，产出 `lessons.candidates`：

| kind | 触发 | 候选说的是 |
|---|---|---|
| `downgrade` | 出现 L4→L2 这类回落 | 证据为何消失？如何防止再发生？ |
| `stagnation` | 最近 3 个事件完成度不变且未达 L5 | 是优先级问题还是被阻塞？ |
| `superseded_decision` | 某决策取代了另一决策 | 原判断为何失效？ |

候选 id 由 `sha1(kind + 对象标识)` 前 6 位生成，**稳定可复现**——同一信号永远得到同一个 id，不会每次重跑都冒出新候选。

> **幂等陷阱**：去重时只能排除「已驳回」和「已转成经验条目」的候选。若把所有已存在的 open 候选都排除，而末尾又只保留 dismissed，open 候选就会在"消失—重现"之间交替，破坏幂等。这是实现时必须守住的细节，校验器已覆盖候选去重检查。

### 2.2 人/AI 把候选确认为经验

候选不是结论。人（或 AI）确认后，把它写进 `lessons.items` 并补上：

- `insight` —— 学到了什么（规律、原因）；
- `action` —— 下次遇到该怎么做（可执行动作）；
- `scope` —— 适用范围（capabilities / projects / domains / levels）；
- `source_events` —— 来自哪些历史事件（可点击跳回）。

状态机：`draft → confirmed → retired`。

### 2.3 经验必须被消费，否则只是另一座档案

`next_queue` 在生成任务卡时，会按 `scope` 匹配所有 `confirmed` 经验并附到 `task.lessons`：

```json
{
  "code": "DEMO.API.QUERY.01",
  "level": "L2", "target_level": "L3",
  "action": "tests/unit/ 有对应测试",
  "lessons": [{"id":"L-001","title":"测试记录文件名必须命中 registry hints","action":"..."}]
}
```

匹配规则：空 `scope` 视为全局经验；否则任一维度（能力编码 / 项目 / 能力域 / 等级）命中即相关。校验器会检查任务卡引用的经验**必须是 confirmed**——防止草稿结论被 AI 当真执行。

这就是经验层的闭环：**历史产生信号 → 人确认结论 → 下一轮任务自带结论**。踩过的坑不会再靠"记得"来避免。

## 三、在循环协议中的位置

| 步骤 | 历史/经验层做什么 |
|---|---|
| SCAN | 重算状态 → 比对指纹 → 必要时追加历史事件；刷新经验候选 |
| SELECT | 任务卡附带匹配的成功经验 |
| PLAN / EXECUTE | 决策可引用 `source_events`，执行时看到前人结论 |
| VERIFY | 校验历史链、事件指纹、经验引用、任务卡经验状态 |
| VISUALIZE | 看板「演进历史」「经验库」两视图，能力点内嵌变更历史与相关经验 |

## 四、示例中的真实产出

`examples/demo-shop` 的历史不是编造的，而是真实迭代的结果：

1. `#1 genesis`：初始状态，4 个能力点（DATA L5 / ORDER L5 / PRICE L2 / QUERY L2）。
2. 补上 `test_pricing.py` 与 `PRICE_TEST_RECORD.md` 后重跑 → `#2 change`：`DEMO.CORE.PRICE.02` 从 L2 跃迁到 L5，证据变化 1 项，整体完成度 0.70 → 0.80。
3. D-002（暂缓补测）被 D-003 取代，决策关联变化触发 `#3 change`——**决策演进也会进入历史**。
4. `DEMO.API.QUERY.01` 连续两个事件停在 40% → 候选 `LC-C1CDBB`（stagnation）；决策被取代 → 候选 `LC-E0299A`（superseded_decision）。
5. 人工确认的经验 `L-001`（测试记录命名必须命中 hints）自动附到唯一任务卡 `DEMO.API.QUERY.01`。

连续重跑三次，事件数、指纹、候选 id、任务卡完全一致——幂等成立。示例也演示了另一条治理纪律：**决策被事实超越时用取代链，而不是改写原裁决**。

## 五、使用清单

- [ ] 重跑生成器后，打开看板「演进历史」确认没有意外事件；
- [ ] 出现降级事件时，优先查明原因，不要把降级当成正常波动；
- [ ] 定期清理「经验库 → 待确认候选」：确认有用的写成 `items`，不适用的设 `status: dismissed`；
- [ ] 经验条目务必写 `action`，只有 `insight` 的经验无法进入任务卡发挥作用；
- [ ] CI 中跑 `verify_ledger.py --strict`，把历史链断裂当作阻断性错误。

### 适用边界

每个事件都保存完整 `state_digest`，代价是账本随「能力数 × 事件数」增长。这换来单事件独立回放的能力，适合项目级治理（几十到几百能力点、几十次迭代）。若规模继续扩大，可只保留 diff 并把旧事件快照归档到外部文件，同时在事件中记录归档路径——但那属于工程优化，不改变这里的语义契约。
