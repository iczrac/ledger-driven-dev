# 21 · 节点工作台与看板视图

> 三问之三：**深化看板视图、发散思维、提高项目利用价值，
> 能在对应模块或组件显示 TODO list、issue、测试结果等。**
> 本文给出数据契约、视图设计、健康度公式与发散出来的能力。

## 一、v1.1.0 的看板是「浏览器」，不是「工作台」

模板有 8 个 tab、4 个 `render*` 函数，但：

- `capability_model.next_queue` 有任务卡，模板**完全没有引用**；
- `test_report.json` 只有全局 `verified_coverage` 徽章，没有逐用例明细；
- 没有 `issue` 概念，`pending` 只是全局决策条目的状态过滤；
- 模块/组件卡片只有完成度和文档索引，**看不到这个节点现在要做什么**。

于是项目负责人看完看板，还得回到聊天记录、issue 列表和 CI 日志里找答案。

## 二、数据契约：两份新字段，仍是一份账本

| 字段 | 内容 | 唯一写入点 |
|---|---|---|
| `work_items` | `id / kind(todo\|issue) / scope / status / severity / owner / detail / refs / close_condition` | `work_panel.py add / close` |
| `test_results` | `test_report.json` 的只读投影：`source_sha256 / summary / cases[]` | `work_panel.py sync-tests` |

**派生聚合不落盘**：`work_panel.py nodes` 与看板 JS 用同一条规则按 scope 复算，
所以不会冒出第三份需要同步的事实。投影不含 `generated_at` / `raw_tail`，
保证确定性；`source_sha256` 把「全绿」绑定到原始报告字节。

scope 语义：

```text
PROJECT                 全局，覆盖所有节点
DEMO                    项目级
DEMO.CORE               模块级（含其下所有能力点）
DEMO.CORE.ORDER.01      能力点级（四段式编码）
```

上级作用域向下覆盖，因此模块卡片能同时看到「本模块待办」「项目级 issue」
和「某个具体能力点的 TODO」。

## 三、视图设计（10 个 tab）

### 工作台（控制塔）

8 个指标：未关闭 TODO / 未关闭 Issue / 阻塞项 / 失败用例 /
待裁决决策 / 任务卡 / 绑定用例 / 项目健康度；再往下是四个区块：

1. **证据状态**：新鲜度、verified 覆盖、投影绑定摘要、整体完成度；
2. **最需要处理的三件事**：阻塞 → 失败测试 → TODO，直接给结论；
3. **焦点队列**：按 `blocked → issue → high → 其它` 排序的工作项卡片；
4. **`next_queue` 任务卡**：每张卡带缺口、文档数、以及该能力点的节点工作条；
5. **失败 / 异常用例明细** 与 **证据待补能力点**清单。

### 工作项

全局或按作用域钻取；卡片含作用域、严重度、负责人、关闭人、
关联决策/能力/路径；下方是该作用域的**逐用例测试结果**。
清空搜索并点「工作项」标签回到全局。

### 节点工作条（真正落在模块 / 组件上）

模块地图、架构钻取的模块卡片、能力地图的模块与**每个能力点**都新增一行：

```text
节点工作态  TODO 2 · Issue 1（阻塞 1）· 测试 2/3 · 失败 1 · 健康度 47
            [查看该节点工作项 →]  [展开本节点 TODO / issue / 测试结果 ▾]
```

点击「查看该节点」跳转到工作项视图并自动把作用域设为该编码。

### 发散出来的额外价值

- **健康度**：把「阻塞 / 缺陷 / 失败测试 / 证据新鲜度 / declared 能力」
  压成一个 0–100 的数，Agent 可以直接按它排开发顺序；
- **证据待补能力点**：把「哪些能力只是文件存在、没有实测」列成清单，
  直接对应下一轮取证任务；
- **失败用例明细**：不用离开账本就知道哪个文件、哪个用例挂了；
- **工作项引用**：TODO / issue 可关联决策 id、能力编码与证据路径，
  形成「决策 → 工作 → 测试」的闭环；
- **关闭条件（`close_condition`）**：工作项可声明机器可判定的关闭条件，
  条件被证据满足后仍挂 `open/doing` 会被第 22 条不变量判失败：
  `{"kind":"capability_verified","capability":"X.Y.Z.01"}`（该能力已 verified）、
  `{"kind":"file_exists","path":"governance/test_report.json"}`（路径已存在）、
  `{"kind":"manual"}`（只能人工判定）。判定不了的条件一律视为未满足——宁可漏关，不可误关；
- 全部新视图沿用 `PAGE_SIZE` 分批，规模预算新增 `work_items` 阈值。

## 四、健康度公式（两端完全一致）

```text
health = max(0, 100 − 20×阻塞Issue − 8×其它未关闭Issue
                − 15×失败用例 − 15×(证据非 fresh) − 10×(子树含 declared 能力))
```

`work_panel.py nodes` 与模板 JS `nodeWork()` 用同一公式；
测试用合成账本证明两者口径一致，避免「CLI 说健康、看板说危险」。

## 五、写入纪律与 26 条不变量

```bash
python3 scripts/work_panel.py --target P check --json           # 只读取证
python3 scripts/work_panel.py --target P nodes --json           # 给 Agent 的节点摘要
python3 scripts/work_panel.py --target P sync-tests --apply \
    --approved-by "审批人姓名" --json
python3 scripts/work_panel.py --target P add --kind todo \
    --scope DEMO.CORE.ORDER.01 --title "补边界用例" \
    --apply --approved-by "审批人姓名" --json
cd P && python3 governance/verify_ledger.py --root . --strict
```

所有写动作默认 dry-run，`--apply` 必须人批准，落盘走
`ledger_io.write_ledger`（账本与看板 EMBED 一起同步）。

校验器从 21 条扩到 **24 条**，新增：

| 不变量 | 拦什么 |
|---|---|
| `work_items_valid` | id 重复、kind/status/severity 非法、scope 无法解析、缺 title；**关闭条件已被证据满足却仍 `open/doing`** |
| `work_item_refs_valid` | 引用了不存在的决策 / 能力 / 非法引用类型 |
| `test_results_binding_valid` | 手填 `source_sha256` 伪造成全绿、用例状态非法、数量不符 |

## 六、升级与空态

`upgrade.py` 的 **M8** 只新增 `work_items: []`，并在项目已有
`test_report.json` 时顺手生成可验证投影；不改 `entries` / `history` /
`capability_model`。项目尚未升级或完全没有工作数据时，
工作台显示空态、全部能力按 `declared` 显示，**不伪装成 verified**。

## 七、反模式

- 把 TODO 写进聊天记录、外部 issue 系统或第二份 Markdown 台账；
- 手改 `work_items` / `test_results` 或看板 HTML 里的数字；
- 为了让徽章变绿手填 `source_sha256`；
- 删 `history.events` 或旧工作项来减小体积（append-only 是历史可信前提）；
- 在项目里改 CSS / DOM 做「专属工作台」——换版面只能改模板并发版再由 M6 归一。
