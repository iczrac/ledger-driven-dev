# 03 · 编码与成熟度

## 一、四段式能力编码

每个能力点有一个唯一编码：

```
{项目}.{模块}.{能力域}.{序号}
   │      │       │       │
   │      │       │       └── 两位序号，01 起
   │      │       └────────── 能力点域代码（READY / ORDER / PRICE ...）
   │      └────────────────── 模块代码（DATA / CORE / API ...）
   └───────────────────────── 项目代码（DEMO / MYPROJ ...）
```

示例：`DEMO.CORE.ORDER.01` —— Demo 项目核心模块下的订单能力，第 1 个。

### 编码规则

- **唯一且稳定**：一经分配不随名称变化。改名不影响编码。
- **不复用**：能力废弃时标记 `retired`，不删除、不把序号给新能力。
- **序号语义**：同一模块同一能力域有多个实现时递增（`.01`、`.02`）。
- **机器可读**：编码是图节点主键，供规划器与编码代理定位。

### 为什么需要编码

没有编码时，「订单能力」在不同文档里可能指不同东西。有了编码，决策、看板、代码注释、AI 任务都能用同一个 ID 精确指代，自动编程才能落地。

## 二、L0-L5 成熟度

完成度不是主观百分比，而是逐级证据判定的结果：

| 等级 | 名称 | 判定规则 | 需具备的证据 |
|---|---|---|---|
| L0 | 规划中 | 仅出现在规划文档，无契约/源码 | — |
| L1 | 契约已定 | `contracts/` 有契约文件 | 契约 |
| L2 | 代码已落地 | `src/` 有实现模块 | 契约 + 实现 |
| L3 | 单测覆盖 | `tests/unit/` 有对应测试 | + 单测 |
| L4 | 运行验证 | `docs/test_records/` 有测试记录 | + 测试记录 |
| L5 | 生产闭环 | 有治理门禁 + 运行台账/看板 | + 治理门禁 |

**完成度 = level / 5**。L5 为 100%，L2 为 40%。

### 逐级判定，缺证据即停

生成器按顺序判定，取最高达成级；某一级缺证据则停在该级之前。例如：

- 有契约、有实现、有单测，但没有测试记录 → L3（60%），不会算 L4；
- 有实现但无契约 → L2（40%），不会因为「代码不少」就给高分。

### 关键不变量

1. **完成度只由证据判定，禁止手填**。账本里没有「completion」字段可改。
2. **可回落**：删掉测试记录后重跑，等级从 L4 掉回 L3。这让完成度始终反映现状。
3. **L5 需开关**：只有 `registry.json` 里 `governance_gate=true` 且有 `governance/` 目录的项目才能授予 L5，其他项目最高 L4。避免空头闭环。

### 证据如何匹配

**v2.1.0 起，证据只来自 registry 声明，不回读账本。** 这是一条硬约束，不是风格：
从账本派生 hints 会让账本变成自己的函数——抹掉证据就再也算不回来，等于把
「记录」冒充成「证明」。实测代价是 20 个 L5 在证据抹空后全部塌成 L2。

匹配优先级：

1. **`caps[].tests`（显式声明，推荐）**：精确路径列表，逐条校验「存在且已入库」；
   声明了却找不到的文件**按缺失处理并打印告警**，不静默保留。
2. **`caps[].hints`（关键词回退）**：`unit_test_dir` 下文件名含任一关键字。
   扫描范围限定在能力自己所属的项目子树（由 `impl` 前缀推导），不跨项目。
3. **`caps[].test_records`（显式声明）**：L4 测试记录的精确路径；同样优先于 hints。

其余各级：

- **契约**：实现路径命中 `contracts_dir`；
- **实现**：`caps[].impl` 指定的 glob 命中真实文件；
- **治理门禁**：`governance/` 存在且 `governance_gate=true`。

为什么推荐 `tests` 而不是 `hints`：关键词会碰撞。实测中 `security` 同时命中
「证券池」与「安全边界」，`risk` 让「风险平面」和「Barra 模型」共用同一份四件套，
而项目根写 `.` 时旧的 monorepo 扫描会把别的项目同名测试也算进来。显式声明是
可 diff、可审阅的，碰撞在写下那一刻就暴露，而不是在账本里悄悄繁殖。

## 三、规划（next_action）

每个能力点还有一个机器可读的规划字段：

```json
{
  "next_level": 4,
  "next_action": "docs/test_records/ 有测试记录",
  "status": "in_progress"
}
```

- `next_level`：下一个要攻克的等级；
- `next_action`：达成该等级需要的**具体证据要求**（不是空泛的「继续优化」）；
- `status`：由等级派生——L5 `operational`、L2+ `active`、L0-1 `planned`。

这三项由生成器从等级规则推导，重跑不丢。它们是循环协议 SELECT 步骤的输入——下一章讲。
