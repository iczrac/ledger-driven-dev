# 20 · 测试架构按开发模块重组

> 三问之二：**测试文件是否按开发模块重新组织架构？**
> v1.1.0 的诚实答案：不是。17 个 `tests/test_*.py` 扁平排列、按脚本横切命名，
> 没有模块归属，也没有任何机器能检查的映射。v1.2.0 把它变成可复算事实。

## 一、为什么扁平不算架构

方法论要求「文档 - 测试 - 实际代码 - 账本记录」用四段式编码
`PROJ.MODULE.DOMAIN.NN` 对应，但仓库自己的测试却是：

```text
tests/
├── _base.py
├── test_agent_gateway.py     ← 按被测脚本命名
├── test_generation.py        ← 横切多个能力
├── test_upgrade.py
└── ...                       共 17 个，无分组、无归属、无校验
```

目录是否好看，和「哪个开发模块由哪些测试守护」是两件事。
后者如果只写在文档里，下一次搬文件就会腐化。

## 二、六个开发模块

| 模块 id | 名称 | 覆盖域 | 测试文件 |
|---|---|---|---|
| `core` | 账本与生成器 | capability_model / history / evidence_tier / verify | 4 |
| `adoption` | 新建与存量接入 | bootstrap / discovery | 2 |
| `routing` | 专家路由与纪律 | route_expert / skills / scenario_matrix | 3 |
| `meta` | 元层：升级、接入、生命周期 | upgrade / agent_gateway / lifecycle / layout | 5 |
| `traceability` | 可追溯闭环 | doc rebuild / architecture / git / graph | 3 |
| `views` | 资产可用、工作台与看板 | asset_bundle / work_panel / board / test_modules | 4 |

共 **6 个模块 / 21 个测试文件**。`platform`、`trace` 这类目录名刻意避开：
它们与 Python 标准库同名，`unittest discover` 会把顶层模块误当成包而导入失败。

## 三、三方自证（单一事实源）

```text
tests/MODULES.json                 模块 → 文件 → 所属脚本的唯一清单
        ⇅ 逐项比对
每个 test_*.py 的 MODULE_ID       文件自证归属（放在 future import 之后）
        ⇅ 逐项比对
run_tests.py: sorted(tests.rglob("test_*.py"))   机器发现口径
        ⇅ 交叉验证
unittest discover -s tests -v     第二套发现，用例数必须相同
```

`scripts/test_modules.py --check` 校验：

1. 模块 id 唯一、不与标准库冲突；
2. 清单里的文件全部存在，且都在 `tests/<模块id>/` 下；
3. 每个文件有 `MODULE_ID` 且与目录、清单三者一致；
4. 清单文件集合 == `rglob` 结果（多一个、少一个都失败）；
5. `owner_scripts` 指向的脚本真实存在；
6. 文件语法可解析（ast）；
7. `run_tests.py` 的默认 pattern 与清单口径一致。

`--emit-md docs/generated/TEST_MODULES.md` 从同一份清单渲染说明，禁止手改。

## 四、推广到被治理项目

`--target P` 只读读取目标项目账本，把每个能力模块的
`doc_index.unit_tests` 汇总成 `test-module-coverage/1`：

```bash
python3 scripts/test_modules.py --target P --json
```

输出 `modules[].status = ok | no-tests` 与 `modules_without_tests[]`。
这让「哪个模块还没有测试」成为机器可查的事实，而不是靠人记忆。
缺口只能由人在 `registry.json` 补 `unit_test` 声明并真正写用例，
不能靠重命名文件假装补齐。

## 五、门禁中的位置

`check.sh` 的 `stage_tests` 现在跑**双口径**：

```text
python3 -m unittest discover -s tests -v
python3 scripts/run_tests.py --dir tests --top . --out <tmp>/repo-tests.json
→ 断言 overall=pass、绑定 21 个测试文件、用例数 ≥ 170
```

`stage_test_modules` 再校验清单与生成文档同步、目标项目缺口报告可跑。
两套发现口径从「各跑各的」变成「互相证明」，这正是 v1.2.0 想补的：
**测试架构本身也要被测试**。

## 六、反模式

- 只把文件搬进模块目录，不改 `MODULES.json` 与 `MODULE_ID`；
- 用 `platform` / `trace` / `test` 等标准库同名目录；
- 直接编辑 `docs/generated/TEST_MODULES.md`；
- 用目录重排代替补齐单测（目标项目缺口只看真实 `doc_index.unit_tests`）；
- 把 `MODULE_ID` 写在 `from __future__` 之前导致语法错误。
