# 19 · 专家与技能升级到「可用」

> 三问之一：**专家和 skill 等工具是否一起升级到可用？**
> v1.1.0 的答案只有「一起发版、绑一个摘要」；v1.2.0 把它补成
> **发版 → 安装 → 绑定 → 校验 → 回滚** 的完整链路。

## 一、v1.1.0 的真实缺口

| 事实 | 后果 |
|---|---|
| `upgrade.py` 只同步 3 个 `governance/*.py` 工具副本 | 目标项目里没有一份 `SKILL.md` / `EXPERT.md` |
| `governance_meta.method_assets` 只有整包 sha256 | 摘要能证明「资产变了」，不能证明「Agent 现在能用」 |
| `route_expert.py` 用硬编码 `EXPERT_CARDS`，不读资产正文 | 用旧专家卡指挥新骨架，路由结果完全一样 |
| `docs/10` 的安装章节是人工 `cp -r` 到用户级目录 | 无人执行、无校验、无版本绑定，升级后不会重跑 |

一句话：**摘要是「知道版本」，不是「可用」**。verify 可以全绿，
但项目里的 Agent 仍在用上一代的技能纪律。

## 二、v1.2.0 的设计：只读部署副本

第一性原理的取舍：要「可用」就必须让 Agent 能读到资产文件；
要「不产生第二事实源」就不能允许目标项目编辑这些文件。
结论是**带哈希的只读部署副本**。

```text
方法论仓库 tag（唯一权威源）
   ├── method_assets.py        整包摘要 → governance_meta.method_assets
   ├── asset_bundle.py M7      逐字节副本 → <P>/.workbuddy/{experts,skills}/<name>/
   ├── ASSET_MANIFEST.json     逐文件 sha256 + 整包 digest
   └── governance_meta.installed_assets.digest（账本内绑定）
              ↑
   route_expert.py 优先读取项目内已安装副本，路由结果携带 assets.digest
```

| 类别 | 内容 | 升级方式 | 是否进目标项目 |
|---|---|---|---|
| A 方法论仓库资产 | `experts/`、`skills/`、`scripts/`、`templates/`、`docs/01-21` | 提交 + 打 tag | **权威源不进** |
| B 只读部署副本 | 8 个 `EXPERT.md` + 20 个 `SKILL.md` | M7 人批准安装 | 是（`.workbuddy/`） |
| C 目标治理骨架 | 3 个工具副本 + 账本字段 + 看板骨架 | M1–M8 | 是 |
| D 账本数据契约 | `ledger_version` | 仍只 fail-closed | 是（数据） |

B 不是第二份规则：副本逐字节相同、清单只记哈希、账本只绑摘要，
**任何手改都会变 drift**，唯一修复方式是重新批准安装。

## 三、五个动作

```bash
python3 scripts/asset_bundle.py --check                         # 定义自检：frontmatter / 数量 / 路径
python3 scripts/asset_bundle.py manifest --json                 # 可安装清单与整包摘要
python3 scripts/asset_bundle.py install --target P --json       # 只读预演（缺/漂移/多余旧版本）
python3 scripts/asset_bundle.py install --target P \
    --apply --approved-by "审批人姓名" --json                   # 人批准后才写盘
python3 scripts/asset_bundle.py verify --target P --json        # 副本 / 清单 / 账本三方一致
python3 scripts/route_expert.py --target P --check-assets --json  # 路由确实读到了资产
```

`install` 幂等：内容一致的不重写；旧清单里的过期副本**只有在其内容仍等于
清单记录哈希时**才移除，被人改过的列为 `stale_protected` 并保留，交人决定。

| verify 错误 id | 含义 |
|---|---|
| `missing` | 副本缺失 |
| `drift` | 副本内容与权威源不一致 |
| `manifest_missing` / `manifest_digest` / `manifest_files` / `manifest_hash` | 清单缺失、摘要或文件集合漂移 |
| `ledger_binding` | 账本没绑当前摘要（需要 M7） |

## 四、路由真的消费资产

`route_expert.py` 的 `load_assets()` 读取真实 frontmatter
（`name` / `description` / `Triggers:`），`asset_root()` 优先选项目内
`.workbuddy/`，否则回落方法论仓库。输出新增：

```json
"assets": {"root_kind":"installed","status":"ok","digest":"...",
           "expert_count":8,"skill_count":20,
           "missing_experts":[],"missing_skills":[]}
```

卡片里引用的专家/技能缺文件即 `status=incomplete`，路由自动追加
「先重新安装」前置条件。`--check-assets` 单独做 fail-closed 校验。

## 五、升级链路（M7）

`upgrade.py` 从版本五轴扩到**六轴**（新增 `installed_assets`），
迁移 M1–M6 → **M1–M8**，`post_upgrade` 11 → **18 步**，verify 9 → **11 项**。

- `plan` 只读列出 `installed`（digest / 缺失 / 漂移 / 受保护旧副本）并列入 M7；
- `apply` 先做统一备份（备份清单含全部安装路径与 `created` 列表），
  再安装副本，最后写 `governance_meta.installed_assets`；
- `verify` 新增 `installed_assets` 与 `work_panel` 两项，`upgrade_complete`
  要求 8 项关键检查全 pass；
- `rollback` 逐文件恢复旧副本，并按 `.workbuddy/` 白名单移除
  升级前不存在的新产物（**不碰用户自己的技能文件**）。

## 六、反模式

- 在项目里编辑 `SKILL.md` 来「让校验变绿」：制造第二份规则，下次升级必被覆盖；
- 手改 `ASSET_MANIFEST.json` 或 `installed_assets.digest`：伪造版本绑定；
- 把整包资产复制进 `governance/`：违反文件布局清单，会被 `--diff` 判越界；
- 跳过 `--approved-by`：AI 不得自行改写可用资产；
- 只发 tag 不跑 M7：摘要变了但副本还是旧的，`verify` 会一直 warn。
