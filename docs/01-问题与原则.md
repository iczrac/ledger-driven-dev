# 01 · 问题与原则

## 一、这套方法从哪来

它不是一个理论设计，而是从一个真实的多项目研发现场「长」出来的。当时的痛点很具体：为了查清一个数据口径问题，翻遍了聊天记录、十几份 HTML 报告、几个人的笔记，最后发现结论改过三次、互相矛盾。于是有了第一个共识：**结论不能散着放**。

收敛过程中逐步形成了三层结构：

- 第一层：把结论收进一份账本（解决「找不到、说不清」）；
- 第二层：把项目结构、能力、完成度也收进来并可计算（解决「看不明、信不过」）；
- 第三层：把账本变成 AI 可消费的输入，驱动下一轮迭代（解决「接不上、自动不了」）。

## 二、四类熵增

| 症状 | 典型表现 | 后果 |
|---|---|---|
| 决策散落 | 结论在聊天、报告、会议纪要里各有一份 | 无法追溯，反复推翻同一件事 |
| 能力不清 | 说不出模块做到什么程度、谁负责 | 重复建设，交接困难 |
| 文档脱节 | 文档路径写死在报告里，索引看不见 | 文档变成墓碑，没人维护 |
| AI 断链 | 没有机器可读的任务与证据要求 | 自动编程只能靠猜 |

## 三、五项设计原则

### 1. 单一事实源（Single Source of Truth）

所有重大决策、裁决、待办只写进一份 `DECISION_LEDGER.json`。旧报告不再维护，只作历史证据保留。看板从这份文件渲染，不另存一份状态。

**为什么重要**：一份事实源意味着一次写入、一处生效。散落是矛盾的温床。

### 2. 证据判定，禁止手填

能力完成度由生成器扫描真实文件系统得出——契约、实现、单测、测试记录、治理门禁逐级判定 L0-L5。任何人（包括 AI）都不能直接写「这个能力 90%」。

**为什么重要**：手填的完成度必然乐观化、必然过期。可计算的完成度才有决策价值。

### 3. 可复算（Recomputable）

重跑生成器即刷新全部派生数据：完成度、组件树、文档索引。证据消失，等级自动回落。看板内嵌数据也由生成器同步，杜绝手工改图。

**为什么重要**：系统要能自愈。人会忘、会写错，重跑不会。

### 4. 索引可见、可点开

能力点和规划都能索引到对应文档，且在看板上可见、点击即打开。组件以真实嵌套树呈现，逐层展开。索引路径统一为仓库根相对，校验存在性。

**为什么重要**：看不见的索引等于没有；点不开的链接让人放弃。

### 5. 如实记录不做

`deferred`（暂缓/另案）是一等公民。决定不做的事也要写进账本并说明原因，而不是假装完成或从记录里删除。

**为什么重要**：很多风险来自「以为做了其实没做」。诚实的账本比好看的账本有用得多。

## 四、这套方法不做什么

- **不替代版本控制**：账本记录决策与能力，代码历史仍归 Git。
- **不替代项目管理**：迭代节奏、排期、分工仍由团队流程决定。
- **不追求大而全**：只记录「重大」决策；日常琐碎沟通不必入账。
