# 22 · 反向回流：让真实项目的摩擦回到方法论

> 一句话：升级链原来只有下行管道（方法论仓库 → M1–M8 → 目标项目），本章补的是上行管道。

## 为什么需要这条管子

在此之前的版本演进里，真实项目试用踩到的坑，绝大多数只落在目标项目自己的
`work_items` 里，方法论仓库既看不见、也无法证明自己修过。结果就是：规范在
示例项目里自测全绿，一进真实的存量项目就连续踩同类坑。

从第一性原理看，有三条不可回避的事实：

1. **治理系统的产出不是版本号，而是「下一个项目不再重踩」**。测试全绿只证明规范
   *自洽*，不证明规范 *有效*；有效性的唯一证据是真实项目的摩擦数据。
2. **基线不可后补**。要判断一次升级有没有改善，必须在动作之前记录状态。这个原则和
   「先确认数据正常，再重建快照」是同一条：没有基线，改善无法被证伪。
3. **未启用不等于通过**（见 [11 · 证据分层](11-证据分层.md)）。观察通道把「字段没填」
   也变成一条可追踪记录，而不是让校验器默默放行。

因此升级流程被拆成两个不可交换的时点：

```
PRE_UPGRADE（1 步）  →  M1–M8  →  POST_UPGRADE（19 步，末步回流）
   baseline.jsonl                    observations.jsonl
        └──────────── diff ────────┘   → triage → 四产物 → 下一个版本
```

顺序不可逆：先升级再采集，就永久丢掉了「升级前到底有哪些摩擦」。

## 观察契约 `ledger-observations/1`

观察包是 JSONL，一行一条，字段如下（完整实现见
[scripts/ledger_feedback.py](../scripts/ledger_feedback.py)）：

| 字段 | 含义 |
|---|---|
| `schema` / `obs_id` | 契约版本；`obs_id` 由 `来源 + 阶段 + 症状 + 轴` 派生，手改症状会被指纹校验抓到 |
| `source_ref` | `project:<registry.json 字节 sha256 前 12 位>`，不含路径与项目名，干净 clone 可复现 |
| `method_version` | 采集时目标项目的版本，用于和权威源对比 |
| `phase` | `baseline` / `upgrade` / `verify` / `runtime` / `manual` / `after-upgrade` |
| `symptom` / `repro` / `expected` | 看到了什么、怎么复现、本来应该怎样 |
| `affected_axis` / `severity` | 六轴及扩展轴（`registry` / `access` / `lifecycle` / `scale` / `hygiene` …）；`low/med/high` |
| `evidence_sha` | 绑定原始证据片段的字节摘要，不是引用一句转述 |
| `proposed_change` | 建议方向，不替人下结论 |
| `status` / `disposition` / `artifact_ref` / `reason` | 由 triage 填写，见下节 |

采集源（全部只读，**绝不写目标项目**）：`work_items` 中未关闭项、未确认的
`lessons.candidates`、`upgrade_log` 迁移事件、结构性字段缺口、目标项目校验器的
`fail / na / warn`、版本落差、校验器代际，以及 `--note` 人工补充。

### 脱敏是数据驱动的

代码里**不硬编码任何具体项目名词**。项目标识从目标项目自己的 `registry.json` 与
`capability_model.projects` 动态提取后中性化；绝对路径、邮箱、密钥形态按形状替换；
需要更强的脱敏时用 `--terms <外部词表文件>` 注入，词表文件不进仓库。这样门禁不会
因为某个通用技术词被误伤，也不会把某个项目的名字写进全国规范。

## 四产物 triage 协议

每条观察必须收敛成以下之一，否则 `check` 判定闭环未完成：

| disposition | 产物形态 | `artifact_ref` |
|---|---|---|
| `invariant` | 新增 / 修正一条不变量 | 校验器模板路径 |
| `scenario` | 新增一条场景矩阵轴或负向场景 | 场景脚本 / 矩阵文档 |
| `migration` | 新增或修正一条迁移 M / 流程步骤 | 升级脚本路径 |
| `regression` | 新增一条「先失败后通过」的回归测试 | 测试文件路径 |
| `wontfix` | 明确不修 | 可不填，但 **必须写 reason** |

`check` 会校验：字段齐全、`obs_id` 与内容指纹一致、已关闭项的 `disposition` 合法、
四产物类的 `artifact_ref` **指向真实存在的文件**、关闭理由非空。也就是说
「口头说已修」不算收敛，必须有落盘的产物。

## 命令

```bash
# 1) 升级前：只读基线（dry-run 默认不写盘）
python3 scripts/ledger_feedback.py export --target P --json
python3 scripts/ledger_feedback.py export --target P \
    --out feedback/baseline.jsonl --phase baseline --apply --approved-by <人>

# 2) 升级后：复导，与基线 diff
python3 scripts/ledger_feedback.py export --target P \
    --out feedback/observations.jsonl --phase after-upgrade --apply --approved-by <人>

# 3) triage 成四产物
python3 scripts/ledger_feedback.py triage --file feedback/observations.jsonl \
    --obs-id OBS-xxxxxxxxxxxx --disposition regression \
    --artifact-ref tests/meta/test_feedback.py --reason '说明' \
    --apply --approved-by <人>

# 4) 闭环校验 / 聚合
python3 scripts/ledger_feedback.py check  --file feedback/observations.jsonl --json
python3 scripts/ledger_feedback.py report --file feedback/observations.jsonl --json
```

写盘一律需要 `--apply --approved-by <人>`；`export` 永远不写目标项目。

## 验收标准

一次 adopt / upgrade 要算「闭环成立」，必须同时满足：

- 升级前后各有一份观察包，且两者可 diff（幂等 digest 稳定）；
- 至少一条观察被 triage 成四产物，且 `check` 的 `feedback_closed ≥ 1`；
- 至少一条回归测试能被重放成**先失败、后通过**（见
  [tests/meta/test_feedback.py](../tests/meta/test_feedback.py) 的
  `test_closed_without_disposition_fails_then_passes`）。

每个 tag 在 [RELEASE_CHECKLIST.md](../RELEASE_CHECKLIST.md) 里必须写明本版的
`feedback_closed` 数，否则不算完整发布。
