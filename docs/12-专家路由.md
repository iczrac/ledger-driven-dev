# 12 · 专家路由：一套方法，多个负责人

前十一篇解决的是「账本怎么可信」。这一篇解决另一个问题：**谁来动手**。

一个真实项目同时存在三种压力：历史资产不能破坏、新项目不能空转、任何改动都要可验证。把它们交给同一个「万能 Agent」有两种失败方式：要么为了快而覆盖历史文件，要么为了稳而什么都问人。答案是按证据与权限拆分角色，再用确定性路由把任务交到正确的人手里。

## 一、从第一性原理推导

| 原理 | 推导出的约束 | 在代码里的落点 |
|---|---|---|
| 证据先于叙述 | 先读文件系统，再听任务描述 | `route_expert.py` 只读扫描 ledger/registry/源码/测试/文档 |
| 单一事实源 | 同一时刻只允许一位专家有写权限 | 路由输出唯一 `route.expert` 与 `writes` 范围 |
| 最小权限 | 审计只读、执行不碰派生字段、盘点只写草稿 | 六个专家的 `EXPERT.md` 权限矩阵 + 脚本保护 |
| 确定性 | 相同输入必得相同输出 | `route_expert.py` 无模型调用、无时间戳、可重复比对 |
| fail-closed | 冲突或损坏时停下来，不猜 | `needs_clarification` / `route.blocked` / 退出码 2 |
| 可交接 | 每一步都留下事实、前置条件、停止条件 | `route.handoff` 结构 |

一句话：**路由不是「猜谁更懂」，而是「谁在此时有资格写什么」**。

## 二、六种专家

| 专家 | 状态/意图 | 能写什么 | 核心纪律 |
|---|---|---|---|
| `expert-router` | 任何入口 | 什么都不写 | 冲突 ask，不挑一个继续 |
| `greenfield-architect` | 空目录 + 新建 | 治理骨架、registry、`D-001` 接入事实 | 不预填等级、不覆盖既有文件 |
| `project-archaeologist` | 有历史资产、无账本 | `registry.draft.json`、`ADOPTION_REPORT.md` | 只读盘点，草稿≠事实 |
| `ledger-steward` | 已有可信账本 | `entries`、`lessons.items` | 决策取代链、经验进任务卡 |
| `evidence-auditor` | 校验/CI/账本损坏 | 只读 | 失败即冻结，不自己修账本 |
| `loop-executor` | 有 next_queue + 编码意图 | `src/**`、`tests/**`、`docs/test_records/**` | 一次一卡，不碰派生字段 |

原有 `ledger-steward` 仍是循环的默认负责人；新增五种角色不是替代它，而是把「接入前」和「写入后」的边界补齐。

## 三、路由优先级

```
账本 JSON 损坏 ─────────────────────────→ evidence-auditor（冻结）
显式模式与现状冲突 ─────────────────────→ 提出澄清，禁止覆盖
已有账本 + 校验/编码/决策/经验 ─────────→ auditor / executor / steward
有历史资产 + 无账本 ────────────────────→ project-archaeologist
registry 有、账本无（或反之）───────────→ 补缺口，不重建既有资料
空目录 ───────────────────────────────→ greenfield-architect
多个强意图并列 ────────────────────────→ needs_clarification，本轮止步
```

`--mode greenfield|brownfield` 只在人已确认边界时使用；它不会覆盖事实，冲突会被显式报告。

## 四、两条完整路径

### A. 新建项目（greenfield）

```bash
# 0. 先路由：空目录 + 新建意图
python3 scripts/route_expert.py --target /path/to/new --intent "新建项目"

# 1. 架构师生成骨架（registry 来源记为 template）
python3 scripts/init_project.py --target /path/to/new \
  --code NEW --name "新项目" --intent "新建项目"

# 2. 人工只维护 modules[]：列确有证据路径的能力
# 3. 校准 → 生成 → 校验
cd /path/to/new
python3 governance/build_capability_model.py --root . --dry-run
python3 governance/build_capability_model.py --root .
python3 governance/verify_ledger.py --root . --strict
```

完成后重新路由，默认进入 `ledger-steward` 的 SELECT→PLAN→EXECUTE 循环。

### B. 历史项目（brownfield）

```bash
# 0. 先路由：有代码/测试/文档但无账本
python3 scripts/route_expert.py --target /path/to/legacy --intent "历史项目，接手"

# 1. 考古专家只读盘点，先看报告
python3 scripts/discover_project.py --target /path/to/legacy --dry-run

# 2. 人确认候选模块、警告与 hints 后写草稿
python3 scripts/discover_project.py --target /path/to/legacy

# 3. 人工精简 governance/registry.draft.json（删除非能力文件、合并重复域）

# 4. 无损接入：草稿 → 正式 registry，账本 provenance 记录来源
python3 scripts/init_project.py --target /path/to/legacy --mode adopt \
  --from-draft /path/to/legacy/governance/registry.draft.json \
  --code LEG --intent "接手历史项目"

# 5. 对照真实等级，不要因为历史代码多就预填完成度
cd /path/to/legacy
python3 governance/build_capability_model.py --root . --dry-run
python3 governance/build_capability_model.py --root .
python3 governance/verify_ledger.py --root . --strict
```

`discover_project.py` 不修改源码、不覆盖 `registry.json`、不写账本；重复运行默认跳过既有草稿，只有人显式加 `--force` 才覆盖。`init_project.py --mode adopt` 同样跳过既有治理文件，并在账本里留下 `provenance` 与 `D-001` 接入事实。

## 五、交接协议

路由 JSON 的核心不是专家名字，而是 `handoff`：

```json
{
  "expert": "project-archaeologist",
  "confidence": "high",
  "reason": "发现历史资产但缺少可信账本；先只读发现，再无损接入。",
  "skills": ["project-discover", "ledger-scan", "ledger-verify"],
  "writes": ["governance/registry.draft.json", "governance/ADOPTION_REPORT.md"],
  "preconditions": ["dry-run 盘点结果需人工确认"],
  "handoff": {
    "facts": ["项目状态=brownfield", "ledger=absent registry=absent"],
    "open_questions": [],
    "next_expert": "evidence-auditor",
    "stop_if": ["发现报告未经确认前不得覆盖任何既有文件"]
  }
}
```

任何一项缺失都视为路由未完成。专家完成后必须**重新路由**，因为写操作会改变项目状态：草稿生成后状态仍是 brownfield；骨架建立后变成 governed，负责人自然切换到 `ledger-steward`。

## 六、反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 让一个 Agent 同时盘点、初始化、编码 | 历史文件被覆盖，账本来源不明 | 按状态换专家，每步重新路由 |
| 用户说「新建」就直接初始化非空目录 | 存量资产被破坏 | 检查 `detected_mode`，冲突先澄清 |
| 把草稿直接复制成 `registry.json` | 假能力、误命中路径、等级虚高 | 人工精简 + dry-run 对照 |
| 校验失败后顺手改 `level` 让它变绿 | 账本失去可信性 | 冻结，由生成器从证据重算 |
| 路由 `confidence=low` 却当高置信执行 | 错误决策被包装成确定结论 | 转交 `open_questions` 给人 |

```bash
python3 -m unittest discover -s tests -v

```
