# 25 · 专家团自动编排（Expert Run）

> **一句话**：`route_expert` 告诉「该谁做」，`expert-run` 告诉「这条交接链怎么落地」——
> 把 P0 的多跳 `handoff.chain` 展开成逐跳契约、分类命令与一份**人工批准包**，
> 默认 dry-run 零执行，人只在写点批准。这是"全 AI 驱动"里机器可自治的那一半。

## 一、为什么需要它

v2.4.0 之前，「专家团接管全流程」靠编排层人肉：读 `EXPERT.md`、挑命令、判断哪条要批准、
口头转达下一位专家。P0（未发版）修好了路由——未识别指令 fail-closed、`route` 意图归位、
交接链 `chain` 落地——但「链 → 行动」仍是断点。

`expert-run` 补这一环，核心不是"更聪明"，而是**更确定**：
- 机器自动做它能自治的：展开契约、分类命令、生成批准包、流转交接；
- 人保留必须保留的：注册、解冻、归档、升级 apply 这类写入授权。

## 二、三条第一性原理

### 1. 零新判定权
编排结果完全由既有确定性组件决定：

```
run = f(intent, target, route_expert.build, EXPERT_CARDS, commands_for)
```

负责人 = 路由负责人（测试断言 `route.expert` 一致）；契约 = 同一份 `EXPERT_CARDS`；
命令 = `commands_for`。编排器自己不做任何业务裁决，不判断"该不该做"。

### 2. 默认 dry-run、零执行
不跑任何命令、不写任何文件、不碰账本。产物是「计划 + 批准包」，
不是替人执行。这与复述门、场景预检一脉相承：**声明归声明，执行归执行**。

### 3. 权限授予者 ≠ 被授权者
含 `--approved-by` / `--apply` / `register` / `unfreeze` / `archive` 的命令
一律归入批准包，只由人执行。AI 不给自己开权限——否则等于把 v2.2 堵死的伪造洞
在审批层重新打开。

## 三、命令分类（fail-closed）

| 类别 | 判据（按优先级） | 处置 |
|---|---|---|
| `approval` | 命中 `--approved-by` / `--apply` / `register` / `unfreeze` / `archive` / `freeze`；或命中写命令（init_project / discover_project 非 dry / upgrade / lifecycle 等）且无只读标志 | 人批准后执行 |
| `readonly` | 命中 `--check` / `--diff` / `--json` / `--dry-run` / `--strict` / `verify` / `check.sh` 等只读标志 | 可直接执行 |
| `manual` | 无法判定（如内联 `python3 -c`） | 交人工，不自动执行 |

优先级是关键：**写授权标志永远压过只读标志**。含 `--apply --json` 的命令仍判 approval。
保守原则：宁可归 approval，绝不把可能是写的命令判成 readonly。

## 四、输出契约（schema `expert-run/1`）

```json
{
  "schema": "expert-run/1",
  "verdict": "ready | needs_clarification | blocked",
  "route": { "expert": "evidence-auditor", "confidence": "high", "intents": ["verify"] },
  "chain": [
    {
      "index": 0, "expert": "evidence-auditor",
      "contract": {
        "expert_md": "experts/evidence-auditor/EXPERT.md",
        "skills": ["ledger-guard", "..."], "writes": []
      },
      "commands": [
        { "command": "bash scripts/check.sh", "class": "readonly", "reason": "..." }
      ],
      "readonly_count": 4, "approval_count": 0, "next_expert": "ledger-steward"
    }
  ],
  "approval_bundle": { "commands": [], "count": 0, "note": "..." },
  "summary": "交接链 3 跳，只读命令 9 条，需批准 0 条"
}
```

退出码：`0` = ready；`1` = blocked / 需澄清（fail-closed，`chain=[]`，批准包为空）。

## 五、用法

```bash
# 看交接链与批准点（人类可读）
python3 scripts/expert_run.py --target P --intent "校验账本不变量"

# 交给平台/Agent 消费批准包（JSON）
python3 scripts/expert_run.py --target P --intent "校验账本不变量" --json

# 与复述门联动：先结构化意图，再编排
python3 scripts/expert_run.py --target P --intent-file intent.json --json
```

## 六、fail-closed

路由未通过（元指令、多意图竞争、生命周期阻塞）时，`chain=[]`、批准包为空，
只给 `halt_reason`——不生成任何可执行动作。这与 [24-复述门](24-复述门.md) 同一纪律：
**意图没被听懂，机器不往下走**。

## 七、边界（诚实说明）

- **不自动执行**：v2.5.0 的 `expert-run` 只产出计划与批准包，不代跑命令。
  真正的"自动跑门禁"由人/平台拿批准包去执行——这是刻意保留的安全边界。
- **不判定业务优先级**：它只展开路由结果，业务取舍仍由人 + `ledger-steward`。
- **不引入新事实源**：批准包是内存产物，不落盘成第二个账本；权威源仍是 `route_expert`
  与 `EXPERT_CARDS`。
