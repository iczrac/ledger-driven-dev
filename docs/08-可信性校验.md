# 08 · 可信性校验

这是整套方法最底层的一章。前面所有章节都在讲「怎么建」，这一章讲「怎么确认没坏」。

## 为什么需要它

一套方法如果宣称：

- 「单一事实源」——那它必须保证事实源内部自洽；
- 「证据驱动、禁止手填」——那它必须能检测出有人手填了；
- 「索引可见可点」——那它必须能检测出失效的链接。

否则这些承诺都是空话。人会犯错，AI 会幻觉，文件会被删，账本会被手改。**熵增是默认状态，校验是对抗它的唯一手段。**

所以从第一性原理出发：一个「可信系统」的定义性特征不是「它现在是对的」，而是「它能在变错时被发现」。

## 24 条不变量

`verify_ledger.py` 把下列约定变成可执行检查：

| # | 检查项 | 防的是什么 |
|---|---|---|
| 1 | `entry_ids_unique` | 决策 id 重复 / 空值，指向混乱 |
| 2 | `encoding_format` | 编码格式错误，图节点主键失效 |
| 3 | `encoding_unique` | 两个能力共用一个编码，引用歧义 |
| 4 | `completion_matches_level` | 手填完成度——最核心的防作弊检查 |
| 5 | `next_action_present` | 未完成能力没有下一步，循环卡死 |
| 6 | `evidence_tier_valid` | tier 不是 `declared` / `verified`，假绿灯口径失守 |

| 9 | `doc_paths_exist` | 文档索引指向不存在的文件，假链接 |
| 10 | `component_paths_exist` | 组件树路径失效，架构图与现实脱节 |

| 14 | `board_embed_synced` | 看板与账本不一致，人看到的是旧数据 |
| 15 | `history_chain_consistent` | 历史 seq 断裂 / 指纹前后不衔接（删改中间事件） |
| 16 | `history_event_fingerprints` | 事件的 `state_digest` 被篡改后与记录指纹不符 |
| 17 | `history_state_encoding` | 历史快照里混入非法能力编码 |
| 18 | `history_current_matches` | 当前账本状态与末事件不一致（手改能力状态） |
| 19 | `lessons_valid` | 经验 id 重复、状态非法、confirmed 缺洞察/行动、事件引用悬空 |
| 20 | `lesson_candidates_dedup` | 候选重复或与已确认条目冲突，经验库腐化 |
| 21 | `queue_lessons_confirmed` | 任务卡引用了草稿经验，AI 消费未定论结论 |
| 22 | `work_items_valid` | 工作项 id / kind / status / severity / scope 非法或重复 |
| 23 | `work_item_refs_valid` | 工作项引用了不存在的决策、能力编码或路径 |

其中 `completion_matches_level` 是完成度的信用基石：**completion 必须等于 level/5**；
`history_chain_consistent` / `history_event_fingerprints` / `history_current_matches`
合起来是历史的信用基石：**删不掉、改不了、也瞒不过**。有人手改 `"completion": 0.99`
或偷偷删掉一条降级事件，校验器立刻抓出来。

第 6–8 条由 v0.5.0 的证据分层引入（见 [11](11-证据分层.md)），第 22–24 条由 v1.2.0 的
节点工作台引入（见 [21](21-节点工作台与看板视图.md)）：后者把「TODO / issue 字段合法」
与「测试结果投影确由当前报告派生」也变成账本内部可验证的事实，不需要 CI 或外部系统配合。

指纹由校验器独立实现、与生成器交叉验证——两处规范一旦漂移，检查立刻失败，不会出现「自己写、自己验」的自证循环。

## 使用方式

```bash
# 人类可读输出
python3 governance/verify_ledger.py --root .

# 机器可读，接入 CI 或 AI 工作流
python3 governance/verify_ledger.py --root . --json

# 严格模式：有失败返回退出码 1，适合 CI 门禁
python3 governance/verify_ledger.py --root . --strict
```

配合生成器的正确顺序：

```
修改代码/文档 → 重跑生成器 → verify --strict → 提交
```

把 `verify --strict` 放进 pre-commit hook 或 CI，账本腐化就无法进入版本库。

## 校验器自身的可信

一个只会说 PASS 的校验器毫无价值。验证校验器有效的办法是**负向测试**：故意注入腐化，确认它能抓到。

对示例账本注入腐化：

- 重复编码 / 手改完成度 / 失效文档路径 → 报出 `encoding_unique` / `completion_matches_level` / `doc_paths_exist` 三个 FAIL；
- 篡改历史事件指纹 / 清空已确认经验的 `action` → 报出 `history_chain_consistent` / `lessons_valid` 两个 FAIL，其余仍 PASS。

这说明检查真实生效，不是摆设。注意校验器不能替代幂等测试：本轮还专门连续重跑三次生成器，确认事件数、指纹、候选 id、任务卡完全一致——候选去重实现曾有一个 bug 导致 open 候选交替消失/重现，是靠幂等测试而非校验器发现的。两类验证互补。

## 校验的边界

- 它检查**结构自洽**，不判断内容对错。文档写得好不好、决策是否合理，仍需人判断。
- 它检查**路径存在**，不保证文件内容仍有效。一份过时的测试记录文件名还在，校验器仍会通过——内容质量需另行把关。
- 它依赖生成器先跑过。若账本里压根没有 `capability_model` / `history` / `lessons`，相关检查会明确报 FAIL 提示重跑——所以正常流程永远是「先生成，再校验」。
- 它验证历史**未被篡改**，但不验证历史事件**记录的理由是否真实**。事件由生成器从文件系统派生，来源可信度取决于被扫描的文件本身。

明确边界，才不会误以为「校验通过 = 一切正确」。
