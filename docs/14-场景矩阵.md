# 场景矩阵：从第一性原理检查流程覆盖

> 本文回答一个反向问题：不是「我们做了什么」，而是「**在哪些情况下，这套方法会给出错误或危险的结果**」。
> 覆盖结论不靠作者声明，靠 `scripts/scenario_matrix.py` 的单一定义 + `tests/test_scenarios.py` 的真实探针。
> 机器可读表格见 [generated/SCENARIO_MATRIX.md](generated/SCENARIO_MATRIX.md)。

## 一、先问系统到底是什么

这套方法的本质不是「文档模板」或「看板」，而是：

> **在多参与者的时间流里，把项目状态压缩成一份可复算的事实源，并让任何一次动作都能被判定是否安全。**

关键词有三个，缺一不可：

| 词 | 含义 | 直接推出的约束 |
|---|---|---|
| 多参与者 | 人、AI、CI、未来的接手者会交替读写 | 必须能回答「谁在改、谁批准、有没有人同时改」 |
| 时间流 | 状态会变，证据会过期，决策会被推翻 | 必须能检测「读完之后世界变了」 |
| 可复算 | 结论由证据生成，不由叙述生成 | 任何「已完成」都得能重跑出来 |

v0.7.0 之前，前两点被隐含处理了：账本有历史指纹链（时间），专家路由有最小权限（参与者），
但**没有把「时间 + 参与者」的交叉情形当作独立场景检查**。这就是本次审计要找的东西。

## 二、六条公理（推导，不是清单）

从上面那句话往下拆，只需要六条，且每条都能推出一组场景：

- **A1 状态完备**：任一时刻必须能回答「在哪 / 去哪 / 谁在改 / 凭什么 / 谁批准」。
  → 推出批准门、任务领用、退役记录、目标与实际的差异。
- **A2 证据有效**：结论来自可复算证据，而且证据必须**对当前源码有效**。
  → 注意「有效」不是「真实存在」：一份三个月前跑过的测试报告是真实文件，但不是有效证据。
- **A3 单点写入**：同一事实只有一个写入点，写入者权限由路由确定。
  → 推出并发互斥、幂等、看板同步。
- **A4 时间可逆**：历史不可篡改，且能检测并发覆盖与执行中断。
  → 推出指纹链、CAS、断点续跑、git 追踪。
- **A5 未知即停止**：版本、路径、完整性存疑时 fail-closed。
  → 推出损坏冻结、版本契约、扫描截断告警、脱敏。
- **A6 边界闭合**：进入 / 冻结 / 归档 / 移交 / 退役 / 失效都有明确出口。
  → 系统不仅要会「开始」，还要会「停止」；只进不出的方法在真实项目里必然被绕过。

**A2 与 A6 是 v0.7.0 的两个盲区**：A2 只做了空间维度（证据文件存在吗），没做时间维度（证据还新吗）；
A6 只做了入口（新建 / 接入），没做出口（冻结 / 归档 / 退役）。

## 三、场景空间怎么收敛

场景不是拍脑袋列出来的，而是六个维度的乘积，再按「是否会改变系统决策」筛掉等价类：

```
生命周期态 × 变更类型 × 并发参与者 × 时间/版本 × 运行环境 × 失败与授权
   (8)      ×   (9)    ×    (6)     ×    (5)    ×   (7)   ×    (7)
```

全笛卡尔积没有意义。判据是：**如果两个场景触发的检查项和允许动作完全相同，就合并**。
v0.8.0 收敛为 44 个场景、6 个轴。v1.0.0 的反问补上了第七个轴——**接入**：
此前「参与者」被隐含在 A3 单点写入里，只检查「谁在改」，没检查「谁被允许改、权限谁授予」。
于是新增 U（升级，规则本身随时间变化）与 G（接入）两组共 6 个场景：

```
生命周期态 × 变更类型 × 并发参与者 × 时间/版本 × 运行环境 × 失败与授权 × 接入身份
   (8)      ×   (9)    ×    (6)     ×    (5)    ×   (7)   ×    (7)    ×   (4)
```

v1.1.0 的反问又补上第八个轴——**规模**：项目变大后，固定的是治理文件数，
增长的是账本体积、历史事件快照与浏览器 DOM；此前没有预算、分页与基准。
新增 U3（资产漂移）、F8（版面漂移）、S1（体积/DOM 超预算）、S2（全量重算成本）四个场景。

v1.2.0 的三问又补上第九、第十个轴——**资产可用性**与**工作态可见性**：
专家/技能是否在项目里真能加载、测试是否按模块归属、模块节点上能否看到 TODO / issue /
逐用例结果。新增 U4（项目内手改已安装副本）、U5（升级后仍用旧专家卡）、
V1（节点看不到工作项）、V2（伪造测试结果投影）、V3（新项目无工作态数据）、
T6（测试模块归属漂移）六个场景。

现在是 **60 个场景、6 条公理、10 个轴**，全部落在 `scripts/scenario_matrix.py` 的 `SCENARIOS`。

关键设计：这份定义同时驱动三样东西——

```
SCENARIOS ──┬── --emit-md → docs/generated/SCENARIO_MATRIX.md（给人看）
            ├── --check   → 定义自检（id 唯一、covered 必须有探针、gap 必须写代价）
            └── tests/test_scenarios.py → 逐项跑探针（给机器看）
```

所以「已覆盖」是**复算结果**，不是一句会腐化的自我声明。文档里写「支持冻结」而测试没跑过，矩阵自检会直接失败。

## 四、审计发现的真缺漏（v0.7.0 → v0.8.0）

按「会不会导致错误结论」排序，前五项是公理级缺口，不是锦上添花：

| # | 缺漏 | 违反 | 后果 | 修复 |
|---|---|---|---|---|
| 1 | 测试报告只按**文件名**匹配，不绑定文件内容 | A2 | 测试跑过后改源码，`verified` 仍挂着 → **时间维度的假绿灯** | `run_tests.py` 输出 `evidence_binding`（逐文件 sha256）；生成器 `check_freshness()` 重算，任一变化即回落 `declared`；`--strict-evidence` 拒绝未绑定报告 |
| 2 | 生成器无条件覆盖账本 | A3/A4 | 两个 Agent 或「人改了 + AI 后写」会静默丢失决策 | `--expect-fingerprint` 乐观并发控制（CAS）；指纹不符退出码 2，不写盘 |
| 3 | 没有冻结 / 归档 / 退役状态 | A6 | 发布窗口、交付归档、能力下线都无流程出口，只能靠口头约定 | `lifecycle.py` 把状态写进**账本内**（`lifecycle` / `retired_caps` / `execution`），不新建第二事实源；同步看板 EMBED，不碰历史指纹链 |
| 4 | 任务卡只是「建议」，没有执行中状态 | A1/A4 | 长任务中断后无法知道谁在改、锁会不会卡死 | `claim` / `release` 领用记录；guard 对超时锁告警；同码不同 actor 的重复领用被拒 |
| 5 | 解冻 / 归档没有批准人 | A1 | AI 可以自行解除安全边界，审计时无法追责 | `unfreeze` / `archive` 强制 `--approved-by`，批准人写入 `lifecycle.approved_by` 与 append-only `log` |

另外两项属于「把散落判断收敛成统一入口」：

- **版本契约**：`ledger_version` 早就有，但没人检查。现在生成器与 `scenario_guard` 都拒绝跨版本直写。
- **外部/时间前置条件**：新增 `scenario_guard.py`，输出 `scenario-preflight/1`（14 项检查、`allowed_actions` / `blocked_actions`、`route_hint`），把「现在能不能动」变成一次只读调用。

### 为什么不把新检查塞进 24 条不变量

`verify_ledger.py` 的 24 条检查的是**账本内部自洽**（编码、指纹链、经验引用、看板同步）：
给它一个打包后的账本文件就能跑，不需要当前源码、不需要知道现在几点、不需要知道谁来写。

而证据新鲜度、并发指纹、冻结状态、git 完整性、批准人，全部依赖**账本之外的上下文**。
混在一起会让「可信」变成两个不同含义的词，也会让旧账本在本来没坏的情况下莫名其妙 FAIL。
因此分层：`verify` 回答「账本有没有坏」，`scenario_guard` 回答「现在能不能动它」。

矩阵里没有把它涂成一片绿。`partial` 与 `gap` 都是已知且**刻意保留**的：

### 仍然缺漏的部分（诚实边界）

| 类别 | 场景 | 代价 / 何时会咬人 | 触发升级的条件 |
|---|---|---|---|
| partial | T4 git 历史被重写 | 本地无法证明远端没有强制推送 | 需要服务端保护或提交签名，超出纯文本方法范围 |
| partial | L10 模块拆分 / 重命名 | 编码稳定，但没有 new→old 自动映射表 | 出现跨项目引用编码时 |
| partial | C8 目标架构变更 | 只报告差距，不自动回写 registry | 刻意：避免文档解析误差直接污染唯一事实源 |
| partial | P6 CI 与本地差异 | Python 版本 / 时区 / 大小写敏感未做矩阵 | 出现平台相关失败时 |
| partial | E6 非 UTF-8 / Windows 路径 | 统一 UTF-8 与相对路径；`fcntl` 锁在 Windows 降级为告警 | 有 Windows 贡献者时 |
| partial | F7 多人同时改 registry.json | 网关只**检测**内容摘要漂移，冲突仍由 git 人工裁决 | 需要自动三方合并时 |
| partial | S2 生成器全量重算成本 | 按能力逐个扫 docs/tests，接近 `O(能力 × 文件)`；1000 能力基准 4.4s，只有告警没有增量索引 | 超过 1 万能力 / 2 万文件且门禁耗时不可接受时 |
| **gap** | **E7 monorepo 多项目 / 跨仓依赖** | `registry.project.root` 只描述单项目；无联合门禁、跨项目依赖图与联合升级 | 需要独立的 workspace 层，本期未做 |
| by-design | G4 绕过网关直调底层脚本 | 有 shell 的 Agent 仍可直接写账本 | 需要 OS 级隔离，超出纯文本方法范围 |

`by-design` 项不是缺漏，是有理由拒绝：自动重试 flaky 测试会把不稳定伪装成通过（F3）；
AI 替人决定业务优先级会破坏最小权限（F2）；生成器需要写权限，但审计者用 guard/verify 只需只读（E4）；
方法论项目不应持有外部数据源凭据（C9）；把策略执行点伪装成安全沙箱（G4）会给出错误的信任。

## 六、四条端到端流程

### 1. 新建（L1 → C1 → P1）

```bash
python3 scripts/route_expert.py --target P --intent "新建项目"
python3 scripts/init_project.py --target P --code MYPROJ --name "项目名"
# 编辑 P/governance/registry.json —— 唯一需要手工维护的清单
python3 scripts/scenario_guard.py --target P --json        # 先确认允许写入
cd P && python3 governance/build_capability_model.py --root . --dry-run
cd P && python3 governance/build_capability_model.py --root .
```

### 2. 接手历史项目（L2 → L4 → C8）

```bash
python3 scripts/discover_project.py --target P --dry-run   # 只读
python3 scripts/discover_project.py --target P             # 草稿 + 报告，人工确认
python3 scripts/init_project.py --target P --mode adopt --from-draft P/governance/registry.draft.json --code LEG
python3 scripts/architect_from_docs.py --target P
python3 scripts/compare_graphs.py --target P              # 规划 vs 实际，带专家顺序
```

### 3. 日常迭代（P2 / P4 / C6 —— 三条容易踩的并发线）

```bash
# 读取阶段：把指纹带在手上
FP=$(python3 -c "import json;print(json.load(open('governance/DECISION_LEDGER.json'))['capability_model']['history']['current_fingerprint'])")
python3 scripts/scenario_guard.py --target P --expect-fingerprint "$FP" --strict

# 执行阶段：领用任务卡，避免两个执行者同时写
python3 scripts/lifecycle.py --target P claim --code MYPROJ.CORE.X.01 --actor agent-1
python3 scripts/run_tests.py --dir tests --out governance/test_report.json
python3 governance/build_capability_model.py --root . --test-report governance/test_report.json \
  --expect-fingerprint "$FP" --strict-evidence
python3 scripts/lifecycle.py --target P release --code MYPROJ.CORE.X.01 --actor agent-1
```

`--strict-evidence` 是这一步的核心：它保证 `verified` 一定是**这次**源码跑出来的，不是上一次留下的徽章。

### 4. 发布冻结 → 归档移交（L6 → L7 → L8）

```bash
python3 scripts/lifecycle.py --target P freeze --reason "发布窗口" --actor release-bot
python3 scripts/scenario_guard.py --target P --strict     # 写动作全部被阻止，返回 2
python3 governance/verify_ledger.py --root . --strict    # 只读取证仍可用
python3 scripts/lifecycle.py --target P unfreeze --approved-by "审批人姓名"
python3 scripts/lifecycle.py --target P archive --approved-by "审批人姓名" --reason "交付完成"
```

归档是**不可写终态**：需要继续开发就复制出新项目，不要复活旧账本——否则历史链会被改写成「从未交付过」。

### 5. 升级 + 多 Agent 接入（T2 → U1/U2 → G1/G2）

```bash
python3 scripts/route_expert.py --target P --intent "升级治理骨架" --json  # → platform-steward
python3 scripts/upgrade.py --target P plan --json                          # 只读
python3 scripts/upgrade.py --target P apply --approved-by "审批人姓名"     # 备份 + 加字段
# 按 plan.post_upgrade 的 19 步重跑报告 / 生成器 --strict-evidence / verify / board / budget / assets / installed / work-panel / test-modules / guard / layout
python3 scripts/upgrade.py --target P verify --json
python3 scripts/agent_gateway.py --target P register \
  --agent ci-agent --role loop-executor --approved-by "审批人姓名" --apply
python3 scripts/agent_gateway.py --target P status --json   # 取 fingerprint / registry_sha256
python3 scripts/agent_gateway.py --target P request --agent ci-agent \
  --action claim --code MYPROJ.CORE.X.01 --expect-fingerprint "$FP" --json   # dry-run
python3 scripts/agent_gateway.py --target P request --agent ci-agent \
  --action claim --code MYPROJ.CORE.X.01 --expect-fingerprint "$FP" --apply  # 才写
```

顺序是硬约束：**没有 `access` 登记时网关默认拒绝**，所以「多 Agent 接手」必然先经过一次人批准的升级。
`deny` 后不得换 agent id 重试，回到 `expert-route` 重新分派。

## 七、反模式

- **把场景矩阵当清单存档**：定义改了却不重跑 `--emit-md`，文档立刻腐化；门禁会拦下漂移。
- **只跑 verify 就写入**：账本没坏 ≠ 现在可以写。冻结、并发漂移、过期证据都查不到。
- **不传 `--expect-fingerprint` 还开多 Agent**：读后写漂移没有任何保护，guard 只会给 warn。
- **用时间戳判断证据新鲜度**：同分钟重跑、跨时区都会误判；一律用内容摘要。
- **另建 LIFECYCLE.json / RUN_STATE.json**：立刻产生第二事实源，违背 A3；状态必须进账本。
- **归档后解冻继续开发**：历史语义被改写；正确做法是复制新项目并保留旧账本作为取证包。
- **只跑 `upgrade.py apply` 不跑 `post_upgrade`**：工具源码变了但证据过期，`verified` 静默回落 `declared`。
- **`deny` 后换 agent id 或直接调底层脚本**：把审计变成事后编造，见 G1 / G4。
