# 24 · 复述门：让意图被听懂之后再路由

## 一、从第一性原理推导

`route_expert.py` 用关键词把人话意图分成 `new/adopt/verify/code/...`。但它有一个
真实的洞：面对「让专家团接管全流程」这类**编排类元指令**，它返回 `intents=[]`，
然后照常给出一条路由——**意图没被听懂，机器却往下走了**。

这不是路由器的 bug，而是职责边界：路由只负责「已明确的意图 → 唯一负责人」，
不负责「模糊意图 → 明确意图」。中间缺一环：

```
人话 → [复述确认] → 明确意图 → 路由 → 执行
         ↑ 缺的这一环
```

补这一环时有个陷阱：如果复述只是让 Agent 用自然语言说一遍「我理解你要……」，
那又造出了一个**不可机读、可伪造的声明面**——和 v2.2.0 花力气堵死的
「声明权 = 伪造权」是同一个漏洞。所以复述门的形态不是「一段话」，而是：

> **结构化声明 + 机器锚定校验**：Agent 把理解写成 JSON，机器校验 JSON 里的
> 每个能力 code 都能在真实 registry / 账本里找到，写入范围不越权，意图不竞争。

这延续了项目一贯的判据：`结论 = f(声明, registry, 账本)`，可复算、fail-closed、
只读。

## 二、intent.json 契约

```json
{
  "schema": "intent-restate/0",
  "raw_intent": "用户原话，原样保留",
  "restatement": "Agent 用自己的话复述的底层目标，不得逐字照抄",
  "intents": ["code"],
  "capabilities": ["PROJ.MODULE.DOMAIN.NN"],
  "write_scope": ["docs/test_records/**"],
  "open_questions": []
}
```

| 字段 | 约束 |
|---|---|
| `schema` | 必须为 `intent-restate/0` |
| `restatement` | 非空且不等于 `raw_intent`——逼出理解增量 |
| `intents` | 合法集合：`new / adopt / verify / plan / code / lesson / route / archive / migrate / access / retire / resume / meta` |
| `capabilities` | 每个 code 必须锚定到 registry 或账本 `capability_model` 的真实条目 |
| `write_scope` | 写入范围合法；只读意图（`verify/route/meta`）必须为 `["none"]` |
| `open_questions` | `meta` 意图必填——编排类指令必须让人确认目标项目与写入边界 |

## 三、八道校验

| id | 判定 | 失败态 |
|---|---|---|
| `schema` | schema 版本匹配 | reject |
| `restate_nonempty` | 复述非空、非原话照抄 | need_clarification |
| `intent_valid` | 意图在合法集合 | reject |
| `cap_anchored` | 能力 code 锚定真实条目（**防幻觉核心**） | reject |
| `scope_valid` | 写入范围在合法集合 | reject |
| `readonly_no_write` | 只读意图不声明写入 | reject |
| `intent_unambiguous` | 无多业务意图竞争 | need_clarification |
| `meta_disclosed` | 元指令带开放问题、须人确认 | need_clarification |

结论聚合：任一 `reject` → reject；否则任一 `need_clarification` → need_clarification；
否则 allow。三态对应退出码 `2 / 1 / 0`。

## 四、接入路由

```bash
# 独立校验
python3 scripts/intent_restate.py --target . --intent-file intent.json --json

# 路由前置：提供 --intent-file 时，route_expert 先跑复述门
python3 scripts/route_expert.py --target . \
  --intent "让专家团接管全流程" --intent-file intent.json --json
```

非 allow 时，路由结果里：
- `restate_gate.verdict` 记录门的结论；
- `needs_clarification.question` 附带各校验的 `fix`；
- `route.blocked=true`，前置条件追加「复述门未放行」。

不提供 `--intent-file` 时行为与旧版完全一致——这是向后兼容约束，
既有路由调用与测试不受影响。

## 五、为什么不用「图形化检查」实现

曾评估用某图形化建模 prompt 规范（SBR/MBSE/KSB，产出 SVG/D3.js）来实现复述门。
结论是**不采纳**，三条：

1. **能力错位**：那是「把图画得更专业」的 prompt 规范，零代码、无校验器、
   无机器可读输出、无退出码，进不了 fail-closed 链。
2. **违背可复算**：若门的判定依据是一张图，就多了不可机读、可伪造的声明面，
   与 `账本 = f(registry, 仓库, 报告)` 冲突。
3. **成本不匹配**：纳入即资产变更，触发整包升级 + 所有项目重新批准；
   而该规范两个月未更新、许可标注不一。

图形可作为「给人看的展示投影」，但门的判定必须来自可机读 JSON 校验。
