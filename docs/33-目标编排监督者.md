# 33 · 目标编排监督者（v2.13.0）

把「目标」变成账本一等公民，并在授权预算内对单一目标做受控自动循环。

## 为什么需要它

到 v2.12.0 为止，路线（`route_expert`）、编排（`expert_run`）、受控写入（`agent_gateway`）、
验证（`verify_ledger`）与场景预检都已就位，但「围绕一个目标反复推进直到达成」仍靠人肉驱动，
且缺三样关键约束：

1. **方向锁**：多轮里专家可能悄悄改目标描述或成功判据，却没有机制发现；
2. **预算**：没有最大循环数，自动循环可能无限跑；
3. **调整升级路径**：需要改目标时，专家应停下来提议而不是直接改。

Goal Orchestrator 补的就是这三点。它**只读监督、不写事实源**，所有落盘走网关。

## 目标对象（`goals/1`）

账本顶层新增 `goals`，初始化为空（`upgrade.py` M9）。每个目标：

| 字段 | 含义 |
|---|---|
| `goal_id` | `G-` 开头的唯一 ID |
| `description` | 目标描述（方向锁锁定） |
| `success_criteria` | 机读判据数组，每项 `id/metric/target/op/value` |
| `max_loops` / `current_loop` | 循环预算与已用轮次（1 ≤ current ≤ max） |
| `status` | `active` / `paused` / `achieved` / `deactivated` |
| `authorized_by` / `approved_by` | 授权人与批准落盘的人（必须人） |
| `created_at` / `updated_at` | UTC 时间戳 |
| `direction_lock` | `sha256(canonical(description + success_criteria))` |
| `proposals` / `audit` | 调整提议与逐动作审计 |

**方向锁**是核心：专有权在 `goal-approve`。任何专家擅自改描述/判据，
第 30 条不变量 `goal_loop_valid` 会因摘要不匹配而 fail。

## 状态机

```
人批准 create → active ──advance──┐
                  │               │ max_loops 用尽
                  │ pause         ▼
                  ▼            deactivated（终态）
               paused ─resume→ active
                  │
                  └─ criteria 全满足 → achieved（终态）

active/paused 需改目标 → propose → 人 approve/reject → 重算方向锁
```

## 每轮循环（`goal_loop.py`，默认 dry-run）

```
1. 取 next_queue 一条与目标相关的任务
2. route_expert.build（blocked / 需澄清 → 停）
3. expert_run.run（只读分工与批准包）
4. verify_ledger --strict（fail → 停）
5. goal_ledger.check_direction（漂移 → 停 + 提议）
6. advance_goal（内存副本，current_loop += 1）
7. evaluate_criteria → achieved / 继续 / 超预算 → deactivated
```

输出结构化轨迹 `{verdict, stop_reason, rounds[], commands[], goal}`；
`commands[]` 是**待批准网关命令**，脚本本身不执行。
`verdict ∈ {achieved, deactivated, stagnated, blocked, verify_failed, direction_drift, no_queue, halted, invalid}`。

**停滞检测（v2.14.0）**：进展指纹 = 当前任务 + 判据相关能力等级 + 方法版本。
连续 `stall_limit`（默认 2）轮指纹不变即判定空转，`verdict=stagnated`、目标暂停
（`goal-pause`），并给四要素结构化提议：先完成队列任务、补证据、再 `resume`。
这避免把「推进预算」误当「推进工作」——dry-run 不写盘时尤其重要。可用
`--stall-limit 1..20` 调整阈值。

dry-run 的验证只跑账本不变量、不把看板 EMBED 作为阻塞项
（内存推进按设计不写盘；真实写回由人逐条 apply 网关命令完成）。验证 fail 立即停，
**先于**判据评估与停滞检测——账本不合规时不会假装推进。

## 使用方式

### 1. 人批准创建目标

```bash
python3 scripts/agent_gateway.py request --target P \
  --agent ledger-steward --action goal-create \
  --goal-id G-001 --title "把 D3 能力点升到 L5" \
  --criteria '[{"id":"c1","metric":"cap_level","target":"METHOD.GOV.D3.15","op":"gte","value":5}]' \
  --max-loops 5 --authorized-by 张三 --approved-by 张三 \
  --expect-fingerprint <fp> --apply
```

`metric` 支持五类（v2.14.0 扩为五类）：

| metric | 含义 | 关键参数 |
|---|---|---|
| `cap_level` | 能力等级与 value 比较 | `target`=能力码、`value`=等级、`op`=`gte`/`eq` |
| `queue_empty` | `next_queue` 为空 | `target` 任意占位 |
| `invariant_all` | 验证无 fail（循环注入结果） | `target` 任意占位 |
| `method_version` | 方法版本语义比较 | `target`=版本串、`op`=`gte`/`gt`/`eq`/`ne`/`lte`/`lt`（别名同义） |
| `level_progress` | 能力等级相对基线提升 | `target`=能力码、`baseline`=基线等级、`value`=提升量、`op`=`gte`/`eq` |

语义版本按数字段比较（`2.9.0 < 2.10.0`），未知 metric / op 一律判 false（fail-closed）。

### 2. dry-run 看轨迹

```bash
python3 scripts/goal_loop.py --target P --goal-id G-001 --json
```

### 3. 人逐条批准推进/失活

```bash
python3 scripts/agent_gateway.py request --target P \
  --agent goal-orchestrator --action goal-advance --goal-id G-001 \
  --expect-fingerprint <fp> --apply
# 超预算：--action goal-deactivate --reason "max_loops 用尽" --apply
# 达标：  --action goal-achieve --apply
```

推进由预算授权，但**仍走网关审计**（身份/CAS/锁/审计一个不少）。

### 4. 调整目标（唯一合法路径）

```bash
# 专家/人提议：只写 proposals，不改目标
... --agent goal-orchestrator --action goal-propose --goal-id G-001 \
    --original-goal "..." --proposed-change "..." --rationale "..." --impact "..." \
    --proposed-description "..." --proposed-criteria '[...]' --apply
# 人批准后才重算方向锁
... --action goal-approve --goal-id G-001 --proposal-id P-001 --approved-by 张三 --apply
```

## 不变量与护栏

- 第 30 条 `goal_loop_valid`：schema、goal_id 唯一、状态枚举、预算单调
  （`0 ≤ current_loop ≤ max_loops`）、终态 `stop_reason` 必填、方向锁一致、
  判据 id 完整、提议四要素齐全且批准人留痕。
- `check_definitions()` 保证 goal 动作 kind/guard 合法；`human_approval` 阻止自批准。
- 目标编排与现有 `expert-run` / `agent_gateway` 完全相容：前者产批准包，后者执行落盘。

## 诚实边界

- 这是**策略性受控循环**，不是 OS 沙箱；能直接写账本的人仍能绕过，但绕不过不变量与审计。
- 达成判定是机读判据，不替代 `verify_ledger` 门禁；两者都过才算达标。
- 看板暂不新增目标进度视图；`goals` 已是账本一等公民，后续可直接投影。
