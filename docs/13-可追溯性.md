# 13 · 可追溯性：五个反问的完整答案

有人用五个反问检验这套方法。逐条回答之前先立规矩：**回答必须能被脚本复现**，否则只是口号。本篇每项都对应一段可执行的流水线与负向测试。

| 反问 | 答案 | 证据脚本 |
|---|---|---|
| 1. 能否重建规范化的项目文档？ | 能：`registry + 账本 → docs/generated/` 三件套 | `rebuild_docs.py` |
| 2. 能否从文档构建清晰的项目目标架构？ | 能：账本投影 → 规划码，手写文档补目标/依赖；模块内依赖图 | `architect_from_docs.py` |
| 3. 能否结合文档的 git 更新跟进模块决策或迭代变更？ | 能：git log 真实路径 → 能力/决策/事件 | `trace_git.py` |
| 4. 规划图 vs 实际图 + 专家规划顺序/执行 + 配套测试？ | 能：能力级 diff + 开发顺序 + 专家指派 | `compare_graphs.py` |
| 5. 架构有规范编码对应文档/测试/代码/账本？ | 能：`PROJ.MODULE.DOMAIN.NN` 全链路索引 | `code_index.py` |

## 一、规范化文档重建

`rebuild_docs.py` 从唯一事实源渲染三份文档，而不是让人肉同步：

```
governance/registry.json ─┐
                          ├→ docs/generated/PROJECT_BRIEF.md     目标 / 范围 / 状态词
governance/DECISION_LEDGER.json ─→ docs/generated/MODULE_MAP.md  模块 → src → 编码
                          └→ docs/generated/CAPABILITY_INDEX.md 编码 ↔ 文档/测试/代码/决策
```

- 文档带 `> 由脚本重建，请勿手改` 标记；改事实源后重跑即可；
- 默认**跳过**既有文件，只有 `--force` 才覆盖——历史人工补充不会被静默吞掉；
- 所有路径相对项目根，账本中的仓库根前缀会被剥离，输出不含机器绝对路径；
- 确定性：同样输入逐字节一致，可进 CI 做漂移检测。

## 二、文档 → 目标架构

`architect_from_docs.py` 读文档，不读代码：

- `PROJECT_BRIEF.md` 的 `## 目标` → `goals[]`；
- `MODULE_MAP.md` 表格 → 模块、扫描入口、模块内编码；
- `CAPABILITY_INDEX.md` 表格 → 能力编码、名称、`依赖: CODE` → `depends_on`，`目标: L3` → `target_level`，代码列 → `impl_hint`（供语义别名配对）；
- **规划码的唯一来源是 `CAPABILITY_INDEX.md`**（账本的确定性投影，无讲解示例）。其他 `docs/**/*.md` 中出现的四段式编码**不新增规划条目**，只能为已存在的码补充 `目标: Lx` 与 `依赖: CODE`。

> 第一性原理：规划图要回答"图纸该有什么"，只能来自账本投影；手写文档里的码常是格式讲解示例（`DEMO.*` / `X.Y.Z.01`）。实测代价：此前扫全部 `docs/*.md` 使本仓 21 个规划码混入 5 个示例码（23.8%），全部误报为 `planned_only`。改为唯一来源后规划码 21 → 16（全 `METHOD.*`），污染归零；手写文档退为增强源。

产物 `governance/TARGET_ARCHITECTURE.json`（schema `target-arch/1`）带 `confidence` 与 `warnings`：没有目标小节、没有 MODULE_MAP、没有编码时不会假装确定，而是明确降级为 `low/medium`。它与 `discover_project.py` 互补：后者是**文件系统 → 现状草稿**，前者是**文档 → 目标图**。

## 三、Git 更新 → 模块决策 / 迭代变更

`trace_git.py` 只调用 `git log --name-only`，不联网、不改仓库：

```
commit 路径 → registry impl/hints + 账本 doc_index → 能力编码
            → 历史 changes 中的编码/路径 → event seq
            → entries[].evidence 中的路径 → decision id
```

产物 `GIT_TRACE.json` 每条提交含：`hash`、`date`、`subject`、`paths`、`modules`、`cap_codes`、`entry_ids`、`event_seqs`、`iteration_signals`（如 `DEMO.CORE.PRICE.02 L2→L5`）。命中不到编码时写警告，不把"没匹配"伪装成"没变化"。

## 四、规划图 vs 实际图 + 专家执行顺序

`compare_graphs.py` 按能力编码做集合比对与等级比对：

| 状态 | 含义 | 指派的下一步专家 |
|---|---|---|
| `aligned` | 规划存在且达到目标等级 | — |
| `in_progress` | 实际等级低于目标 | `loop-executor` |
| `not_started` | 规划有、证据停在 L0 | `loop-executor` |
| `planned_only` | 规划有、生成器未识别 | `project-archaeologist` 先校准 impl/hints |
| `actual_only` | 实际有、规划图未声明 | `ledger-steward` 裁决补文档或废弃 |

`execution_order` 优先消费账本 `next_queue`（已按完成度升序、已带已确认经验与 tier），再补 `planned_only` / `actual_only`。每条都给 `from → to`、动作、专家、前置条件（`先跑 evidence-auditor`）与经验 id。`overall_expert` 由 `expert-router` 给出，因此"谁规划、谁执行、谁验证"是同一个路由体系的一部分，不是另起一套。

`depends_on` 在此被消费：同一 `from → to` 层内做**稳定拓扑重排**，被依赖者先出队；跨层顺序不动。`depends_on` 稀疏或全空时完全退化为 `next_queue` 原序（等价旧行为）。依赖环写入 `dep_cycles` 与 `warnings`，**只告警、不改状态、不改退出码**（shadow 纪律：先证明判得对，才升级为硬门）。

产物双份：`GRAPH_DIFF.json`（机器）与 `docs/generated/GRAPH_DIFF.md`（人读），同样默认非破坏性。JSON 新增 `plan_status`（`absent` / `empty` / `partial` / `present`）：规划图缺失或不完整时，人读报告首行与 `warnings` 明确"漂移结论不可采信"，`execution_order` 不再派 `project-archaeologist` 逐条伪校准，改指 `architect_from_docs.py` 前置步骤。

若规划码与实际码只是段内写法不同（如 `PRICE_02` / `PRICE02`），`shadow_pairs` 给出归一键与两侧原码。若两者**写法不同但 impl 路径相同/有交集且模块码一致**，额外给出 `kind=alias_suspect` 的配对与 `alias_matches`（双向），人读报告单列"疑似同一能力"小节并附 impl 证据。两者都只提示：五态 `status`、`level`、`execution_order` 与专家分派仍按字面码，**不自动合并、不改等级**，须人工裁决后统一编码。已按格式归一配对的不再重复报 alias。

> 第一性原理：语义别名是推断，误报代价高于漏报——两条不同能力共用同一 impl（能力拆分未落盘）时会被误配。实测代价：用 shadow 只晒不否决，把风险留在人工裁决点；模块码一致 + 末段路径对齐 + canonical 去重三道缓解把误报面压到可接受。

## 五、规范编码的全链路对应

编码格式 `{项目}.{模块}.{能力域}.{NN}`（见 [03-编码与成熟度](03-编码与成熟度.md)）是跨 artifact 的唯一身份证。`code_index.py` 产出 `CODE_INDEX.json`：

```json
{
  "code": "DEMO.CORE.PRICE.02",
  "artifacts": {"docs": [...], "tests": [...], "code": [...], "impl_declared": [...]},
  "entry_ids": ["D-003"],
  "event_seqs": [2],
  "commits": ["abc1234"],
  "level": "L5", "tier": "verified"
}
```

`CAPABILITY_INDEX.md` 是它的人类可读版。两者都从同一份 registry/账本推导，因此不会出现"文档说 A、测试叫 B、账本记 C"的分裂。

## 六、一条完整闭环

```bash
python3 scripts/route_expert.py --target PROJ --intent "接手历史项目并补齐规划"

# 1) 规范化文档 → 2) 文档里的目标 → 3) git 变更 → 4) 规划/实际比对 → 5) 编码索引
python3 scripts/rebuild_docs.py --target PROJ
python3 scripts/architect_from_docs.py --target PROJ
python3 scripts/trace_git.py --target PROJ --max-count 50
python3 scripts/compare_graphs.py --target PROJ \
  --git-trace PROJ/governance/GIT_TRACE.json
python3 scripts/code_index.py --target PROJ \
  --git-trace PROJ/governance/GIT_TRACE.json
```

拿到 `GRAPH_DIFF.json.execution_order[0]`，交给 `loop-executor` 开工；完成后重跑生成器与门禁，再重新路由。每一步的产物都是只读证据，不覆盖既有文件。

## 七、边界与反模式

- 文档解析是**结构化抽取**，不是自然语言理解：目标写在自由散文里、没用 `- ` 列表或表格，就抽不出来，会产生 `warnings`。这是刻意设计——宁可明确缺失，也不假装读懂。
- git 映射以**变更路径**为准，不信任 commit message；message 只作展示。
- `target_level` 未写明时默认 L5；想更早收口就在文档写 `目标: L3`。
- 不要把 `docs/generated/` 当人写文档编辑；改事实源再重跑，否则下次 `--force` 会丢失手工内容。
- 不要把 `planned_only` 直接当进度落后：它常常只是 `hints`/`impl` 没配好，先校准再谈开发。

## 八、验证

`tests/traceability/` 下 7 个测试文件共 42 个用例覆盖：生成三件套、非破坏性与 `--force`、无绝对路径、目标/依赖抽取、git 路径映射与事件 seq、planned_only / actual_only 的专家分派、执行顺序与经验携带，以及本轮四项能力缺口（`test_plan_status` / `test_plan_input_scope` / `test_dep_topology` / `test_alias_suspect`）。`bash scripts/check.sh` 把它们与 31 条不变量一起跑。

> 实测代价：本轮新增 4 个测试文件（23 个用例），单测总数 476 → 499；测试模块清单 `tests/MODULES.json` 与 `docs/generated/TEST_MODULES.md` 同步至 42 文件 / 6 模块，`test_modules.py --check` 三方口径一致。
