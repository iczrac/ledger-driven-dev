# 16 · 升级与迁移：规则本身也会过期

## 一、为什么：v0.9.0 漏掉了一个隐含前提

这套方法的一句话定义是：

> 在多参与者的时间流里，把项目状态压缩成一份可复算的事实源，并让任何一次动作都能被判定是否安全。

这句话隐含「**判定所用的规则不变**」。但规则一定会变：生成器、校验器、测试报告脚本、
账本字段、专家卡、技能与看板模板都会升级。于是已接入的项目会掉进五个洞：

| 洞 | 表现 | 后果 |
|---|---|---|
| 工具副本悄悄落后 | `governance/*.py` 是初始化时复制进去的，之后模板改了没人知道 | 用旧规则算出新结论，`check.sh` 只检查**本仓库**的模板/示例同步，管不到目标项目 |
| 升级没有流程 | 只能手工覆盖文件 | 没有计划、备份、回滚、批准人；出事无法证明改过什么 |
| 升级改变证据语义 | 工具源码变了，`evidence_binding` 的逐文件 sha256 失配 | `verified` 静默回落 `declared`，看板看起来"正常"但证据已作废 |
| 专家 / 技能资产漂移（v1.1.0 补） | 专家卡、技能、路由卡、模板、文档随仓库 tag 变了，目标账本没有任何字段记录 | 用 v1.0 的专家指挥 v1.1 的骨架，`verify` 仍全绿 |
| 看板版面漂移（v1.1.0 补） | 同步器只替换 `EMBED` 数据段，24 条不变量也只校验数据 | 项目手改 CSS 或用旧模板，`board_embed_synced` 照样通过，呈现规则分裂 |

`ledger_version` 只解决了「账本数据契约不兼容时 fail-closed」，**没有解决「兼容但要升级」**。
场景矩阵 T2 因此一直标为 `partial`：只拦得住，走不通；v1.0.0 把它升为 `covered`，
v1.1.0 再补 U3（资产）与 F8（版面）。

## 二、先分清楚「升级」的三种意思

不区分这三者，讨论必然错位：

| 类型 | 变的什么 | 谁负责 | 机制 |
|---|---|---|---|
| A 方法论仓库发版 | `CHANGELOG` / tag / 专家 / 技能 / 路由卡 / 模板 / 编号文档 | 维护者 | git tag `v1.6.0`，本文不展开 |
| **B 目标项目的治理骨架升级** | 3 个工具副本 + 账本内版本字段 + 看板骨架 | 项目人批准，`upgrade.py` | **本文主体** |
| C 账本数据契约迁移 | `ledger_version` 1.0 → 2.0 | 人写专用迁移 | 仍然 fail-closed，不自动猜结构 |

A 的**权威源**不复制进目标项目（见 `file_layout.py` 的 `NOT_IN_TARGET`）。它变了以后，
`method_assets.py` 的整包摘要会变，B 的 `plan` 必须列出 M5，`verify` 才肯宣布完成。
v1.2.0 起还有第二层：M7 把 8 份 `EXPERT.md` 与 20 份 `SKILL.md` 装成项目内
**只读部署副本**，逐文件摘要写进 `ASSET_MANIFEST.json` 与 `governance_meta.installed_assets`。
副本不是第二事实源——它逐字节等于权威源、禁止项目内编辑，唯一修复方式是重新人批准安装。
换句话说：**「一起发版 → 绑定整包摘要 → 安装可加载副本 → 校验逐文件一致」四步才叫升级到可用**，
详见 [19-专家与技能可用](19-专家与技能可用.md)。

B 是绝大多数场景，也是「升级后有没有流程」真正问的东西。C 刻意不做自动化：
历史链、决策取代链、经验引用一旦被猜错就无法从账本内部发现，代价远高于手工迁移。

## 三、机制：版本七轴，缺一不可

```
governance_meta（账本内字段，不是新文件）
├── method_version    方法论/工具链版本，如 1.7.0
├── ledger_version    账本数据契约，只接受 1.0
├── upgraded_from     从哪个版本升上来（未升级过的项目标 pre-1.0.0）
├── migrations_applied 已应用的迁移 id
├── upgrade_log       append-only：seq / at / from / to / approved_by / migrations / backup
├── tools             3 个工具副本的权威 sha256
├── method_assets     专家/技能/路由/模板/文档整包摘要（method-assets/1）
├── board_skeleton    去 EMBED 后的看板骨架 sha256（board-contract/1）
├── installed_assets  项目级 .workbuddy/ 内 28 份只读副本的逐文件摘要（asset-bundle/1）
└── ontology_digest   第七轴：本体投影摘要（ledger-ontology/1，v1.5.0 起）
```
另有 M8 初始化的两个账本内字段：`work_items`（节点 TODO / issue）与
`test_results`（`test_report.json` 的可验证投影），见 [21](21-节点工作台与看板视图.md)。

`ontology_digest` 由 `upgrade.py apply` 在 M5 分支写入，**只存可复算的摘要**，
不复制本体内容；`verify` 新增 `ontology_binding`（pass / na / warn），
`scripts/ontology.py check --target P` 会重算比对。删光派生文件也能从
`docs/STANDARD.md` 与各脚本枚举复原，因此它不是第二事实源。见
[23 · 本体投影](23-本体投影.md)。

```json
{
  "schema_version": "1.0",
  "method_version": "2.0.0",
  "upgraded_from": "pre-1.0.0",
  "ledger_version": "1.0",
  "migrations_applied": ["M1-governance-meta", "M2-access-registry",
                         "M4-method-version", "M5-method-assets",
                         "M7-asset-install", "M8-work-panel"],
  "upgrade_log": [
    {"seq": 1, "action": "apply", "from": "pre-1.0.0", "to": "1.7.0",
     "approved_by": "张三", "backup": "20261118T001500Z-74843609", "risk": "low",
     "assets_digest": "<12位>", "board_skeleton": "<12位>",
     "installed_digest": "<12位>"}
  ],
  "tools": {"governance/build_capability_model.py": "sha256..."},
  "method_assets": {"algorithm": "sha256-files-v1", "digest": "<sha256前12位>...",
                    "source": "方法论仓库 tag（权威源，不复制）"},
  "board_skeleton": {"digest": "<sha256前12位>...", "source": "templates/index.html.template"},
  "installed_assets": {"digest": "<sha256前12位>...", "file_count": 28,
                       "manifest": "governance/ASSET_MANIFEST.json"}
}
```

`scripts/upgrade.py` 的 `TOOLING` 是「目标项目相对路径 → 本仓库权威来源」的唯一映射，
`--check` 会验证来源文件存在、迁移 id 不重复、升级后流程引用的脚本存在、
看板权威模板存在，以及 `method_assets.py --check` 的资产齐备性。
`scripts/file_layout.py` 描述「哪些文件会存在」，本脚本描述「用什么版本复算它们」，两者不重叠。

### 八条迁移

| id | 动作 | 需要批准 | 说明 |
|---|---|---|---|
| M1-governance-meta | 写入版本与迁移元数据 | 是 | 不碰 `entries` / `history` / `capability_model` |
| M2-access-registry | 建立默认拒绝的 `access` 登记 | 是 | **升级是多 Agent 接入的前置条件**，见 [17](17-多Agent接入控制.md) |
| M3-tool-sync | 同步 3 个工具副本 | 否（但整次 apply 需批准） | 先备份；副本变化会使证据过期 |
| M4-method-version | 刷新版本号与工具摘要 | 否 | M1 之后运行 |
| M5-method-assets | 绑定整包资产摘要 | 否 | 专家/技能/模板/文档任一变化即触发；权威源仍不进项目目录 |
| M6-board-skeleton | 用权威模板重建看板骨架 | 是 | 只换 CSS/DOM/JS，数据段仍是当前账本；统一备份 `index.html` |
| M7-asset-install | 安装只读专家/技能副本到 `.workbuddy/` | 是 | 写 `ASSET_MANIFEST.json` 与 `installed_assets`；幂等，被人改过的旧副本保留并列 `stale_protected` |
| M8-work-panel | 初始化 `work_items` / `test_results` | 否 | 只加两个字段，投影绑定当前 `test_report.json` 字节；无报告则留空态 |

M1–M5、M8 只加字段；M6 改的是**派生层文件**，M7 改的是**资产层只读副本**，
两者都不改账本历史语义。因为不改写派生状态，`current_fingerprint` 不变，
**不会追加历史事件**——升级不是一次能力变更。M7 的安装产物纳入备份清单；
回滚按白名单只移除「升级前不存在」的副本，不碰用户自己的 `.workbuddy/` 文件。

## 四、怎么用：六阶段流程（有对应流程，不是"跑完脚本就完"）

```
PLAN → SNAPSHOT → APPLY → VERIFY → RE-BASELINE → AUDIT
只读     备份      人批准    只读      重取证      账本内留痕
```

### 1. PLAN（只读、确定性）

```bash
python3 scripts/route_expert.py --target P --intent "升级治理骨架" --json
python3 scripts/method_assets.py --check
python3 scripts/upgrade.py --target P plan --json
```

`upgrade-plan/1` 给出 `from_method` / `to_method`、待应用迁移、3 个工具副本的
`in-sync / drifted / missing`、`assets`（仓库摘要 vs 项目记录摘要）、
`board`（模板 vs 看板骨架）、`installed`（副本 missing / drifted / stale_protected）、
阻塞项、`risk` 与 **19 步 `post_upgrade`**。
plan 不含时间戳，可进 CI 比对；发现以下任一情况直接 fail-closed：

- `ledger_version` 不在支持集合 → 不猜结构，要求专用数据迁移；
- 生命周期 `frozen` / `archived` → 升级是写入动作，先经批准解冻；
- 账本由更新版本的方法论写入 → 升级本仓库，不要降级写新账本；
- 账本损坏 → 先备份并人工修复。

### 2. SNAPSHOT + 3. APPLY（人批准）

```bash
python3 scripts/upgrade.py --target P apply --approved-by 张三 --json
```

`apply` 缺 `--approved-by` 直接拒绝（AI 不得自行升级治理骨架）。它会：

1. 在 `P/.ledger-upgrade/backups/<UTC>-<账本摘要前 8 位>/` 写入
   账本 / 看板 / registry / 3 个工具副本 + `manifest.json`（只存相对路径与 sha256）；
2. 按 M1→M8 顺序加字段、同步工具副本、安装只读专家/技能副本（M7）、初始化工作台字段（M8）、必要时用模板归一 `index.html`；
3. 用 `ledger_io.write_ledger()` **同时**写账本与看板 EMBED（否则 `board_embed_synced` 会挂）；
4. 把批准人、迁移列表、资产摘要、骨架摘要、备份 id 追加进 `governance_meta.upgrade_log`。

重复 apply 是 `noop`：版本、工具、资产、骨架都一致时不备份、不写日志、不写盘。

### 4. VERIFY（只读）

```bash
python3 scripts/upgrade.py --target P verify --json
```

`upgrade-verify/1` 有 **12 项**：账本可解析、数据契约、方法论版本、工具摘要、看板数据同步、
`access` 登记、**资产摘要**、**看板骨架**、**已安装副本**、**本体投影摘要**、**节点工作台**、证据是否需要重绑。
有任何 `block` 退出码 2。`upgrade_complete` 只在版本 / 工具 / 接入 / 资产 / 骨架 /
本体投影 / 已安装副本 / 工作台 / 证据**九项**全部 `pass` 时为真——
`warn` 不等于成功，避免"升级过了"变成一句口头声明。

### 5. RE-BASELINE（最容易漏的一步）

工具副本内容一变，`evidence_binding` 的逐文件 sha256 就可能失配，
`verified` 会回落 `declared`。这不是 bug，是证据分层在正确工作；
**危险的是没人重跑测试**。所以 `post_upgrade` 是升级的组成部分，不是附录：

```bash
python3 scripts/run_tests.py --dir tests --out governance/test_report.json
cd P && python3 governance/build_capability_model.py --root . \
  --test-report governance/test_report.json --strict-evidence
cd P && python3 governance/verify_ledger.py --root . --strict
python3 scripts/upgrade.py --target P verify --json
python3 scripts/board_contract.py --target P check --json
python3 scripts/scale_budget.py --target P --json --check
python3 scripts/method_assets.py --check
python3 scripts/scenario_guard.py --target P --strict
python3 scripts/file_layout.py --diff --target P --strict
python3 scripts/agent_gateway.py --target P status --json
python3 scripts/route_expert.py --target P --intent 校验账本 --json
python3 scripts/asset_bundle.py --check
python3 scripts/asset_bundle.py verify --target P --json       # 逐文件副本校验
python3 scripts/work_panel.py --target P check --json          # 工作台字段自洽
python3 scripts/work_panel.py --target P sync-tests --apply --approved-by 张三
python3 scripts/work_panel.py --target P nodes --json
python3 scripts/test_modules.py --check                        # 测试模块映射
python3 scripts/route_expert.py --target P --check-assets --json
```

顺序不能换：先重跑报告，再用 `--strict-evidence` 重新生成，最后才校验。
只重跑生成器而不重跑报告，会把过期报告继续当 `verified` 用（v0.8.0 修过的假绿灯）。
第 5–7 步是 v1.1.0 新增的三项契约核对：版面、规模、资产；
第 12–18 步是 v1.2.0 新增的七步：可用资产、工作台投影、节点聚合、测试架构与路由资产消费。
完整 19 步以 `plan.post_upgrade` / `upgrade.py check` 的定义为准，不要凭本文手抄。
本文与技能卡里的所有计数都从 `upgrade.py` 的代码常量派生，由 `scripts/acceptance.py`
的验收契约门禁逐行校验；升级时先改常量，再改正文与生成器源文本并重算派生文件，
不要批量替换 `docs/generated/`——手改派生文件会被派生可复算检查拦下。

### 6. AUDIT + 回滚

```bash
python3 scripts/upgrade.py --target P rollback --backup-id <id> --approved-by 张三
```

回滚按 `manifest.json` 逐文件恢复，校验路径不含 `..` 或绝对路径，同样要人批准。
它会在备份目录写一份 `rollback-receipt.json`（记录批准人与恢复清单）；
若备份账本里本来就有 `governance_meta`（半途升级），才额外追加一条 `rollback` 日志——
**升级前状态的账本会被严格还原，不会为了留痕而改写历史**。
注意回滚会把看板一并恢复到升级前骨架，因此回滚后必须重新
`plan → apply → verify` 与 RE-BASELINE，不能只看账本字段就宣布完成。

## 五、升级后流程的状态机

```
pre-1.0.0 ──plan/apply──> 1.7.0（已升级，证据待重绑）
                              │
              ┌───────────────┴────────────────┐
        re-baseline 通过                 re-baseline 跳过
              ↓                                ↓
     verified 恢复 / 门禁全绿            verified 回落 declared
              ↓                                ↓
     注册 Agent（人批准）                 禁止多 Agent 写入
              ↓                        （access 仍生效，但证据不可信）
     expert-route 重新分派
```

**升级与接入的耦合是刻意的**：`M2` 建立 `access` 登记（默认 `agents=[]`），
`agent_gateway.py` 发现没有登记就拒绝一切请求。
因此「想让多个 Agent 接手开发」必然先走一次有人批准的升级，
不会出现「Agent 自己给自己开权限」。

## 六、边界与反模式

- **不是数据迁移器**：`ledger_version` 不兼容时仍 fail-closed；本文只做加字段式升级。
- **不是 OS 沙箱**：备份目录在项目根、不在 `governance/`，避免被布局 `--diff` 判为第二事实源；
  但它是可写的，权限仍由 git / 文件系统负责。
- **不自动合并 `registry.json`**：升级不改唯一手写清单；并发编辑由 git 人工裁决，
  网关用内容摘要做**检测**（场景 F7）。
- **不做自动回滚**：`verify` 失败只报告，是否回滚由人决定。
- **权威源不落地，只读副本才落地**：模板/文档/scripts 仍只在方法论仓库；专家/技能经 M7 装成项目内只读副本，权威源仍是仓库 tag。改动任一资产都会触发目标项目重新批准升级（M5 + M7）。
- **版面由模板统一**：禁止在项目里改 CSS/DOM；骨架归一化必须先备份、后经人批准。
- **规模只告警不降级**：`scale_budget.py` 报预算，由人决定拆项目或归档；生成器全量重算无增量索引（S2）。
- 反模式：只跑 `apply` 不跑 `post_upgrade`；把 `upgrade_log` 复制成 `UPGRADE_LOG.md`；
  在目标项目里手改工具副本、CSS 或已安装的 `SKILL.md` / `EXPERT.md` 后不重跑 `plan`；
  为了让 `verify` 变绿手改 `method_assets.digest` / `installed_assets.digest` /
  `test_results.source_sha256`；把只读副本当成本地可编辑的技能来自行"修 bug"；
  
  用时间戳判断"是否已升级"（一律看七轴摘要）；只跑 `apply` 就宣称专家/技能"已可用"（必须跑
  `asset_bundle.py verify` 与 `route_expert.py --check-assets`）。
- 残留：跨平台 CI 矩阵、monorepo 多项目联合升级（E7）仍未做；生成器全量重算无增量索引（S2）。
  见 [14](14-场景矩阵.md)、[18](18-规模化与版面契约.md)。
