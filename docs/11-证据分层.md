# 11 · 证据分层：区分「写了测试」与「测试真过了」

## 从一个假绿灯说起

L0-L5 成熟度判定有一个根本盲点：它只看**证据文件是否存在**。

一个能力点只要在 `tests/unit/` 下有个 `test_order.py`，哪怕文件是空的、测试是坏的、从没跑过，也会被判为 L3「单测覆盖」。于是出现一个荒诞的局面——一套宣称「证据驱动、消灭假绿灯」的方法，自己就在制造假绿灯。

这不是实现细节的疏漏，而是第一性的断裂：

```
事实层（文件/测试）→ 判定层（生成器算 level）→ 消费层（看板/任务队列/AI 编码）
                          ↑ 断裂点：只检查"文件在不在"，不检查"测试过没过"
```

如果完成度建立在「存在性」之上，那么消费层所有决策——任务优先级、下一步规划、AI 自动编程——都建立在一个可被空文件欺骗的信号上。**可信承诺在最底层漏了。**

## 正交的第二个维度：evidence tier

修复方式不是推翻 L0-L5，而是加一个**正交维度**：

| 维度 | 回答的问题 | 取值 |
|---|---|---|
| `level` / `completion` | 能力做到哪一级 | L0-L5 / 0.00-1.00 |
| `evidence_tier` | 这一级的证据是声明还是实测 | `declared` / `verified` |
| `binding_status` | 测试是否经符号绑定证明测的是本能力 | `bound` / `via1` / `unbound` / `no_impl` / `no_tests` |

- **`declared`（声明级）**：证据文件存在但无运行证据，或符号绑定非 bound（v2.2.0 起）。
- **`verified`（验证级）**：双条件——通过的测试报告中有本能力单测的 `pass`，且符号绑定为 `bound`（测试 import 解析到本能力的实现文件）。

两者正交：一个 L5 能力可能是 `declared`（写了全套文件但从没跑过测试，或测试挂错了实现），也可能被升级为 `verified`（测试真跑过且测的是本能力）。v2.2.0 前只看报告 pass，导致「声明权 = 伪造权」——往 `caps[].tests` 塞任意 pass 路径即可刷 verified；绑定硬门禁把 `verified` 钉死为 `⟺ bound`。看板上每个能力点都显示这两个徽章，假绿灯从「看不见」变成「一眼可见」。

## 测试报告从哪里来

`scripts/run_tests.py` 用**标准库 unittest** 跑测试，产出机器可读报告（零第三方依赖，与项目承诺一致）：

```bash
python3 scripts/run_tests.py --dir examples/demo-shop/tests \
  --top examples/demo-shop \
  --out examples/demo-shop/governance/test_report.json \
  --label demo-unit
```

- `--dir`：含 `test_*.py` 的目录（可递归到子目录）。
- `--top`：import 根，测试里 `from src.xxx` 时 `src` 所在的目录。
- 报告 schema 为 `ledger-test-report/1`，含每个用例的文件、状态、耗时，以及 `overall`。

关键纪律：**导入失败会被计入报告，`overall=fail`；空用例（0 passed）也算失败**。这防止「0 个用例却报 pass」的假通过。

## 生成器如何判定

把报告传给生成器：

```bash
python3 build_capability_model.py --root . --test-report examples/demo-shop/governance/test_report.json
```

判定规则（保守、可解释、幂等）：

1. 报告缺失、schema 不符、或 `overall != pass` → 所有能力保持 `declared`；
2. 报告中某用例 `status=pass`，且其文件名与能力 `unit_test` 证据的 basename 匹配 → 该能力升级 `verified`；
3. 没有匹配 → 保持 `declared`；
4. 不传 `--test-report` 时行为与旧版完全一致（向后兼容）。

`tier` 进入历史指纹：从 `declared` 升到 `verified` 是真实的证据增强，会被历史层记为一次 `change` 事件；但报告的时间戳、耗时等元数据**不进指纹**，所以同一份报告重跑一百次也不会产生噪音。

## 校验器如何防止 tier 腐化

v0.5.0 新增三条不变量（当时共 21 条；v1.2.0 已扩为 24 条）：

| 检查 | 防的腐化 |
|---|---|
| `evidence_tier_valid` | tier 取值必须是 `declared` 或 `verified` |
| `verified_tier_traceable` | verified 必须带 `tier_detail.basis=test_report_pass`、匹配的单测真实存在，且 `binding_status=bound`（v2.2.0）|
| `verified_tier_not_premature` | 低于 L3（无单测）的能力不得标 verified |

校验器不依赖外部报告、离线可跑——它验证的是**账本内部自洽**：任何手改 verified 或伪造依据的行为都会被发现。

## 在循环协议中的位置

证据分层落在 VERIFY 步骤，让「验证」从文字承诺变成机器可判：

```
SCAN → SELECT → PLAN → EXECUTE → VERIFY（跑测试→报告→生成器判 tier）→ VISUALIZE
```

任务卡（`next_queue`）也携带 `evidence_tier` 和 `needs_runtime_verification`：AI 拿到任务时，能立刻知道这个能力是「只有文件」还是「实测通过」，避免把声明级能力当成已验证去规划。

## 与 CI 的衔接

`scripts/check.sh` 已加入「证据分层」阶段：先生成实测报告、确认 `overall=pass`，再跑账本校验与幂等。幂等阶段重跑时带同一份报告，保证 verified 稳态不被误判为漂移。

这就是完整的因果链：**测试真跑了 → 报告证明 → 生成器升级 tier → 校验器确认无腐化 → 看板/任务卡消费真实信号**。假绿灯在这条链上没有藏身之处。

## v1.3.0：报告契约开放化与三态校验

`test_report.json` 从此是**开放契约**：只需 `schema` / `summary` / `cases[]` /
`overall` / `evidence_binding`，不限定由哪个框架产生。标准库栈继续用
`run_tests.py`；其它栈用：

```
python3 scripts/work_panel.py --target P import-report --from ci/junit.xml \
    --adapter auto --source-dir src,tests --apply --approved-by <人>
python3 scripts/work_panel.py --target P sync-tests --apply --approved-by <人>
```

支持 JUnit XML、jest JSON 与任意合规 JSON，自动探测适配器。导入器会用项目根
相对路径重算 `evidence_binding`，因此生成器 `--strict-evidence` 与场景预检的
陈旧证据判定仍然成立。`source_adapter` 只留在原始报告里，账本投影仍只保留
看板需要的字段，不产生第三份事实。

校验器同时改为三态：`pass` 是「已启用且通过」，`fail` 是「已启用但失败」，
`na` 是「能力未启用」。**`na` 绝不计入 `pass`**——24/24 全绿不再能掩盖
「还没接实测报告」。`--require-active` 可把 na 判为失败，供项目按治理成熟度
逐步收紧；不加该参数时既有项目不会因为「尚未启用」而突然红灯。
