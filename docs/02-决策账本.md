# 02 · 决策账本

账本是整套方法的地基。它是唯一允许手工写入重大决策的地方，也是看板与生成器的输入。

## 文件结构

`governance/DECISION_LEDGER.json` 顶层字段：

| 字段 | 含义 |
|---|---|
| `ledger_version` | 账本格式版本 |
| `title` / `purpose` | 展示信息 |
| `last_updated` | 最后更新时间（生成器写入） |
| `owner` | 责任人 / 责任角色 |
| `workflow` | 写入规则（人/AI 都该遵守） |
| `fields` | 各字段释义 |
| `entries` | **决策条目数组**，核心 |
| `module_map` | 模块 ↔ 文档 ↔ 可视化对应表 |
| `architecture` | 可钻取架构（项目→模块→组件树） |
| `capability_model` | 能力模型（生成器写入，禁止手改） |

## 决策条目（entries）

一条完整条目：

```json
{
  "id": "D-001",
  "date": "2026-11-17",
  "title": "订单领域纳入 L5 生产闭环",
  "category": "能力建设",
  "scope": "DEMO",
  "status": "done",
  "supersedes": null,
  "superseded_by": null,
  "decision": "配齐契约、实现、单测、测试记录并接入治理门禁。",
  "rationale": "演示完整的 L1→L5 证据路径。",
  "evidence": ["examples/demo-shop/docs/test_records/ORDER_TEST_RECORD.md"],
  "confidence": "high"
}
```

字段说明：

- **id**：`D-NNN`，一旦分配永不复用。删除条目不留空洞，改状态即可。
- **status**：
  - `proposed` 待裁决 —— 新提案，等确认；
  - `decided` 已裁决 —— 决定做，待执行；
  - `done` 已完成 —— 落地并验证；
  - `deferred` 暂缓/另案 —— 决定不做或延后，需写清理由；
  - `superseded` 已被取代 —— 旧结论被新决策推翻。
- **supersedes / superseded_by**：取代链。新决策推翻旧决策时，旧的标 `superseded` 并指向新的，新的回填 `supersedes`。这样演进过程可追溯，而不是堆叠新报告把旧结论覆盖掉。
- **scope**：适用项目代码或 `ALL`。生成器据此把决策关联到能力点。
- **evidence**：证据路径数组，可追溯到原始文件。看板会渲染成可点开的链接。
- **confidence**：`high / medium / low`，表达结论的确定程度。

## 状态机

```
proposed ──裁决──> decided ──执行验证──> done
   │                  │
   └──不做──> deferred │
                      └──被推翻──> superseded（由新条目取代）
```

## 写入约定

1. **一次写入，一处生效**：不要在报告里另写一份结论，只更新账本。
2. **取代而非覆盖**：改主意时新增条目 + 建立取代链，不直接改写旧 `decision`。
3. **id 单调不复用**：`D-001`、`D-002`……即使条目状态变了，id 不变。
4. **待裁决显性化**：`proposed` 和 `deferred` 在看板「待裁决」视图高亮，提醒关注。

## 与能力的双向引用

账本与能力模型互相指向：

- 决策的 `evidence` 或正文含能力域关键字 → 生成器把它关联到对应能力点；
- 能力点的 `doc_index.decisions` 回列关联决策 id 与状态。

于是从任一能力点能反查「为什么这么定」，从任一决策能正查「影响哪些能力」。详见 [03-编码与成熟度](03-编码与成熟度.md)。
