## 一、四项缺口（全部已实证）

| # | 缺口 | 位置 | 实证 |
|---|---|---|---|
| A | 默认 `--source-dir src,tests` 对 monorepo 产生空绑定却判绿 | `scripts/work_panel.py` | `inputs=0`、`source_digest=e3b0c44298fc1c14`=`sha256(b"")[:16]`，`overall=pass` |
| B | pytest JUnit `<testcase>` 无 `file` 属性 → `verified` 永不升 | `scripts/work_panel.py` `_cases_from_junit` + `build_capability_model.py` `judge_tier` | `cases[].file=""` → `passed_files` 空 → `judge_tier=declared` |
| C | `registry.json` 的 `unit_test_dir="tests"` 与 monorepo 布局失配 | 主仓 `governance/registry.json` | `test_root=P/tests exists=False` → `ev["unit_test"]=[]` |
| D | `hints` 填能力代码（如 `<CODE>.DATA.READY.01`），与测试文件名无公共子串 | 主仓 `governance/registry.json` `modules[].caps[].hints` | 即使修好目录，仍 `declared:47 / verified=0` |

**连带风险（最大）**：当前生成器用现有 registry 重算，47 个能力从账本 `L5:20 / L3:22 / L2:5` 回退到 `L2:46 / L0:1`；`upgrade.py` 明文规定「迁移只允许加字段、不改写 capability_model」，因此**工具同步后不得自动重算账本**。

## 二、不降级配方（三种取值在内存验证）

| 配方 | level 分布 | 降级数 | tier |
|---|---|---|---|
| 现状（原 registry） | L2:46 / L0:1 | 待对比 | declared:47 |
| 仅改目录 | L2:46 / L0:1 | — | declared:47 |
| 目录 + `unit_test` 文件名派生 hints | L3:34 / L2:13 | **0** | declared:38 / verified:9 |
| 目录 + `test_record` 文件名派生 hints | L5:20 / L2:26 / L0:1 | **0** | declared:47 |
| 目录 + UT+TR 合并 hints（**选定**） | L5:20 / L3:14 / L2:13 | **0** | declared:38 / verified:9 |

结论：**以账本既有 `evidence.unit_test` + `evidence.test_record` 文件名派生 `hints`，并修正两处目录，可在「降级数=0」前提下把 verified 从 0 升到 9**。这是「重算不降级」的技术基础。

## 四、S4 边界裁定（第一性原理）

1. **方法论仓能做的**：修工具、加断言、发版 v1.8.0、经 M3/M4/M5/M7 同步工具与重绑摘要到主仓。这些是 `upgrade.py` 允许的迁移。
2. **方法论仓不能做的**：在主仓账本里直接重算 `capability_model`（违反 upgrade 契约）、直接改主仓 `registry.json`（权威数据，非升级迁移）。
3. **因此 P1 的「升 verified」在 v1.8.0 里定位为**：工具与断言就绪 + 一份**独立的人批准数据迁移方案**（备份 → 修 registry hints/目录 → 受控重算 → 降级硬门禁 → 复验），不在本版自动执行。
4. 语义图（R4）仍顺延：P1 未最终满足前不纳入。
